# Инструкции для агента разработки

Этот каталог помогает продолжить или повторить разработку `living-bi-dashboard`. Он основан на реальных проблемах проекта, а не на абстрактном чек-листе.

## Быстрый контекст

- Версия проекта: `0.1.0`.
- Это отдельный дашборд на данных Битрикс24, размещённый рядом с нативным BI-конструктором.
- Приложение работает внутри портала через placement `LEFT_MENU`.
- Galaxy запускает Node-сервер. Gateway передаёт серверу временную сессию пользователя.
- Конфигурация, история версий и настройки хранятся в `DASHBOARD_STATE_PATH`.
- Интерфейс получает только агрегаты, без карточек CRM и сырых персональных данных.

Перед началом прочитайте [README.md](../README.md), [docs/SETUP.md](../docs/SETUP.md), [docs/PROGRESS.md](../docs/PROGRESS.md) и [docs/technical-discovery.md](../docs/technical-discovery.md).

## Правила работы

1. Не добавляйте `.env`, ключи `vibe_api_...`, `vibe_app_...`, `vibe_session_...`, cookie и ответы с персональными данными в Git, логи или документацию.
2. Любое изменение JSON-конфигурации проходит через `validateDashboardSpec`, проверку реальных полей портала и preview агрегатов, если меняются источник, фильтр, агрегат, период или набор виджетов.
3. Новую возможность ИИ добавляйте в трёх слоях: схема конфигурации, серверное получение агрегатов, интерфейс и diff. Одного распознавания фразы недостаточно.
4. Перед завершением запускайте `npm run check` и `npm run audit`. Требование тестового покрытия строк: не ниже 70%; текущая цель проекта выше 80%.
5. После изменений, затрагивающих production, публикуйте Galaxy-версию и проверяйте приложение из пункта меню Битрикс24.

## Карта системы

```text
Битрикс24 placement
  -> vibecode.bitrix24.tech/v1/bitrix-handler
  -> Gateway передаёт X-Vibe-Authorization
  -> Galaxy Node BFF
  -> VibeCode V1 API: агрегаты, поля, BitrixGPT
```

Браузер не получает ключ приложения и токен сессии. Сервер использует ключ приложения вместе с временной Gateway-сессией.

## Реальные проблемы и решения

### 1. Приложение открывается с `INVALID_APP_URL` или «Ошибка при показе приложения»

**Причина:** в объекте приложения настроен placement, но Galaxy-адрес самого приложения не указан как `appUrl`, либо placement привязан к старому адресу.

**Решение:**

1. Укажите Galaxy URL в `appUrl` приложения.
2. Убедитесь, что placement ведёт через `https://vibecode.bitrix24.tech/v1/bitrix-handler`.
3. Обновите страницу портала и откройте приложение из левого меню заново.

`handlerUrl` ведёт на Gateway, а `appUrl` указывает, куда Gateway отправляет уже проверенный запрос. Нужны оба адреса.

### 2. Приложение открылось, но данные недоступны

**Симптом:** интерфейс сообщает, что нужна сессия Gateway, либо агрегаты не загружаются.

**Причина:** Galaxy URL открыли напрямую, сервер вышел из сна, placement передал устаревшую сессию или Gateway не подключён.

**Решение:**

1. Откройте приложение через placement в Битрикс24, а не по прямому Galaxy URL.
2. Проверьте статус Galaxy: сервер должен быть `running`, Black Hole/Gateway должен быть `CONNECTED`.
3. Если сервер `sleeping`, запустите его через VibeCode и обновите страницу портала.
4. Для локальной разработки убедитесь, что в `.env` задан `VIBECODE_API_KEY`.

### 3. Galaxy-сервер работает, но после перезапуска пропадают версии

**Причина:** состояние по умолчанию живёт в памяти процесса или во временном каталоге развёртывания.

**Решение:** для production передайте:

```text
DASHBOARD_STATE_PATH=/data/living-bi-dashboard/dashboard-state.json
```

Каталог `/data` является постоянным томом Galaxy. Историю нельзя хранить только в `/opt/app`.

### 4. При восстановлении версии история разрастается

**Причина:** восстановление было реализовано как создание новой версии на основе старой.

**Решение:** `DashboardStore.restore` выбирает уже существующий снимок текущим. Восстановление не создаёт новую запись. Создание версии происходит только при явном сохранении или применении предложения.

### 5. Интерфейс выглядит работающим, но часть действий ничего не меняет

**Пример:** слева можно выбрать «Задачи», но график остаётся графиком сделок.

**Причина:** левая колонка служит каталогом источников и тестовых записей. В версии `0.1.0` нет операции «создать виджет из выбранной сущности».

**Решение для агента:** либо добавить полноценный flow создания виджета, либо оставить текст и визуальные состояния, из которых ясно, что источник только доступен для будущего виджета. Не выдавайте каталог за переключатель текущего отчёта.

### 6. Сохранённые настройки не видны на графике

**Причина:** поля формы меняют локальное состояние; рендер использует сохранённую конфигурацию из сервера.

**Решение:** показывайте заметную отметку о несохранённых изменениях. После «Сохранить версию» загрузите актуальную спецификацию и данные. Визуальная правка должна менять `groupBy`, `options.orientation`, `options.palette`, `period` и затем перерисовывать данные.

### 7. BitrixGPT вернул некорректный JSON Patch

**Причина:** language model может выбрать неверный путь, пропустить обязательное поле или вернуть неподдерживаемую структуру.

**Решение:**

- принимайте только `add`, `replace`, `remove`;
- разрешайте пути только внутри `title`, `period`, `widgets`;
- валидируйте результат патча через `validateDashboardSpec`;
- при ошибке передавайте модели ошибку инструмента и дайте несколько попыток;
- после исчерпания попыток формируйте заявку для агента разработки вместо технического текста пользователю.

### 8. Поддерживаемая визуальная фраза должна работать стабильно

**Проблема:** фраза «сделай график по менеджерам горизонтальным и в цветах бренда, KPI-карточки подними наверх» ранее зависела от того, насколько удачно модель соберёт JSON Patch.

**Решение:** `createVisualCommandProposal` распознаёт безопасные известные настройки детерминированно. В результате меняются группировка `assignedById`, горизонтальная ориентация и палитра `bitrix24`. KPI в интерфейсе всегда рендерятся до графиков, поэтому команда «подними наверх» закрепляет текущий порядок и может не дать заметного перемещения.

### 9. Команда требует возможности, которой ещё нет

**Примеры:** недельная динамика просроченных задач, новый виджет по отделам, произвольный расчёт.

**Решение:** BitrixGPT формирует копируемую заявку в блоке «Нужна доработка». В заявке должны быть причина, недостающие возможности, ожидаемый результат и критерии готовности. Она не создаёт внешнюю задачу и не меняет CRM.

Это общий путь для любого неподдерживаемого запроса. Техническая ошибка от API или Gateway остаётся технической ошибкой: сначала нужно восстановить доступ к платформе.

### 10. Логический сценарий конверсии

Команда:

```text
Конверсию считай только по новым клиентам, исключи воронку «Тест», период — текущий квартал.
```

Реализована как безопасная конфигурация:

- новые клиенты: `isReturning: false`;
- успешные сделки: `stageSemanticId: "S"`;
- период: `closedAt` за текущий квартал;
- конверсия: вычисляемый KPI `new-client-won / new-client-deals`;
- исключение воронки: `categoryExclusions: ["Тест"]`.

Перед агрегированием сервер получает справочник воронок, находит название «Тест» и добавляет его числовой `categoryId` в `$nin`. Если воронка отсутствует, запрос остаётся рабочим, а интерфейс выводит предупреждение. Для полноценной проверки создайте такую воронку в тестовом портале.

## Тестовые данные

```bash
npm run seed
npm run seed:load -- --deals=2000 --manager-distribution=30:700,32:450,34:350,36:300,38:200 --confirm
```

Малый seed использует префикс `VIBECODE_DEMO_BI`. Нагрузочный набор использует `VIBECODE_LOAD_BI`, требует `--confirm` и защищён от повторного запуска. Seed создаёт новые записи, существующие данные CRM не меняет.

## Минимальная проверка перед передачей проекта

1. `npm ci`
2. `npm run check`
3. `npm run audit`
4. Запустить `npm run dev` и проверить агрегаты с локальным ключом.
5. Задеплоить на Galaxy с `VIBE_APP_KEY` и постоянным `DASHBOARD_STATE_PATH`.
6. Открыть placement в Битрикс24.
7. Проверить: визуальная команда → diff → применение → новая версия → восстановление прошлой версии.
8. Проверить: команда конверсии → preview → diff → применение → обновление показателей.
9. Проверить: неподдерживаемая команда → заявка для агента разработки → копирование текста.
