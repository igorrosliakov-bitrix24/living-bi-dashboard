# Часть I. Требования разработчика

Этот раздел фиксирует требования из исходного PRD. Проектные решения и порядок реализации находятся во второй части документа.

## 1. Результаты проекта

Нужно подготовить два связанных результата:

1. Встраиваемое в Битрикс24 приложение-дашборд на данных портала. Пользователь меняет дашборд в чате с BitrixGPT через API Вайбкода.
2. Статью со сквозным демо: от ограничений нативного BI до работающего сценария изменения отчёта обычной фразой.

## 2. Проблема и продуктовый вывод

- Настройка нативных BI-отчётов требует знаний аналитика: датасетов, вычисляемых полей, метрик и фильтров.
- У BI-конструктора нет REST API для чтения и редактирования отчётов, графиков и метрик.
- Методы `biconnector.*` предназначены для внешних источников и датасетов. Они не управляют BI-отчётами.
- Шаблоны нативных отчётов экспортируются из интерфейса архивом; REST API для этого сценария нет.
- ИИ-агент Битрикс24 работает через фиксированный набор инструментов, в котором нет управления BI-конструктором.
- Продукт строит отдельный редактируемый дашборд рядом с нативным BI, используя данные того же портала.

## 3. Целевая аудитория

| Сегмент | Потребность |
|---|---|
| Руководитель отдела продаж или собственник | Смотреть ключевые метрики и менять отчёт под текущий вопрос без аналитика |
| Администратор портала или продвинутый пользователь | Быстро собирать дашборды по запросу руководства |
| Партнёр или интегратор Битрикс24 | Понять и переиспользовать связку «приложение + встроенный ИИ» на Вайбкоде |

## 4. Термины проекта

- **BI-конструктор:** нативное «Рабочее место аналитика» Битрикс24 с датасетами, дашбордами, метриками, полями и фильтрами.
- **ИИ-агент Битрикс24:** встроенный агент или CoPilot, который использует фиксированный набор инструментов.
- **Вайбкод:** платформа Битрикс24 с API `/v1/...`, серверами Black Hole, AI-моделями, ботами и AI-поиском.
- **BitrixGPT:** модели Битрикс24 семейства `bitrixgpt-*`, доступные через OpenAI-совместимый API Вайбкода.
- **Дашборд проекта:** отдельное приложение с виджетами, JSON-спекой и данными из aggregate API Вайбкода. Это не нативный BI-отчёт.

## 5. Обязательные формулировки и ограничения

1. Приложение не читает и не редактирует нативные BI-отчёты: нужного API нет.
2. Перенос конфигурации нативного отчёта в MVP отсутствует. Аналог отчёта можно воспроизвести по описанию.
3. Формулировка о приватности: «данные не передаются сторонним LLM-провайдерам — BitrixGPT работает в инфраструктуре Битрикс24».
4. Нельзя утверждать, что данные не покидают портал: обработка проходит в контуре Вайбкод/Black Hole.
5. Приложение не заменяет полноценный BI. Числовая агрегация Вайбкода работает по выборке до 5000 записей.
6. Для больших объёмов и сложных аналитических срезов остаётся нативный BI-конструктор.

## 6. Функции MVP

### F1. Дашборд из JSON-спеки

- Типы виджетов: KPI, вертикальный и горизонтальный bar, line, pie/donut, таблица.
- Общий фильтр периода для всего дашборда.
- Возможность переопределить период на уровне отдельного виджета.

### F2. Данные портала

- Сущности: сделки, задачи, компании и звонки, если звонки доступны в entity API.
- Стадии воронок загружаются через `/v1/statuses`.
- Запросы к данным портала работают только на чтение: `list`, `aggregate`, `fields`.

### F3. Чат-редактор

- Чат располагается рядом с дашбордом.
- Используется BitrixGPT через `/v1/ai/chat/completions`.
- Модель применяет изменения через function calling и серверные инструменты.
- Модель не генерирует итоговую спеку свободным текстом.

### F4. Версии и undo

- Каждое применённое изменение создаёт новую версию спеки.
- Пользователь может откатить изменение.
- Ответ чата содержит понятное описание изменений.

### F5. Доступ

- Вход выполняется через авторизацию приложения Битрикс24 с ключом `vibe_app_...` и OAuth.
- Дашборд доступен авторизованным пользователям портала.
- В MVP редактировать дашборд может владелец.

### F6. Тестовые данные

- Seed-скрипт создаёт компании, сделки и задачи.
- Сделки распределены по стадиям и датам за 6–12 месяцев.
- Задачи включают дедлайны и просрочку.
- Создание выполняется через `/v1/{entity}/batch`, до 500 записей за запрос.

## 7. Что не входит в MVP

- Запись и изменение рабочих данных CRM и задач из приложения.
- Чтение или редактирование нативных BI-отчётов.
- Экспорт дашборда приложения в шаблон BI-конструктора для Маркетплейса.
- Несколько дашбордов.
- Публичный шаринг за пределы портала.
- Алерты и рассылки.

## 8. Требуемая архитектура

```text
Битрикс24 (iframe-встройка)
   |
   v
Frontend SPA: дашборд + чат
   | HTTPS; без ключей, только пользовательская сессия
   v
Backend/BFF на Black Hole
   |-- /api/dashboard -> спека, версии -> SQLite или Postgres
   |-- /api/data      -> aggregate, statuses, fields -> Вайбкод
   `-- /api/chat      -> BitrixGPT + tools -> Вайбкод
```

Обязательные решения:

- Ключ `vibe_app_...` хранится только на BFF и не попадает во фронтенд.
- Пользователь работает в пределах прав своей OAuth-сессии.
- Агрегации кэшируются примерно на 5 минут; нужна кнопка ручного обновления.
- Нужно учитывать лимиты 60 запросов в минуту на ключ и 10 запросов в секунду на портал.
- На старте проверяется `GET /v1/placements/available`.
- Предпочтительное размещение — `BI_ANALYTICS_MENU`.
- Если `BI_ANALYTICS_MENU` не даёт auth-контекст или требует слишком сложной собственной сессии, MVP размещается в обычном меню/на странице приложения.

## 9. Требования к JSON-спеке

Спека содержит:

- номер версии;
- заголовок;
- общий период;
- массив виджетов;
- для виджета: `id`, тип, заголовок, сущность, фильтр, группировку, агрегацию и визуальные настройки;
- для вычисляемого KPI: ограниченное выражение над результатами агрегаций.

Пример целевой формы:

```json
{
  "version": 7,
  "title": "Продажи: обзор",
  "period": { "field": "closedate", "preset": "this_quarter" },
  "widgets": [
    {
      "id": "w1",
      "type": "bar",
      "title": "Сумма выигранных сделок по менеджерам",
      "entity": "deals",
      "filter": { "stageSemanticId": "S" },
      "groupBy": ["assignedById"],
      "aggregate": { "fn": "sum", "field": "opportunity" },
      "options": {
        "horizontal": true,
        "sort": "desc",
        "limit": 10,
        "color": "#2fc6f6"
      }
    },
    {
      "id": "w2",
      "type": "kpi",
      "title": "Конверсия в успех",
      "entity": "deals",
      "computed": { "expr": "won / total", "format": "percent" }
    }
  ]
}
```

- Спека валидируется через Zod или JSON Schema.
- Разрешены только известные сущности, реальные поля, поддерживаемые функции и типы виджетов.
- Поля сверяются с `/v1/{entity}/fields`.
- В `computed` запрещён произвольный исполняемый код.
- Версии хранятся полностью и последовательно; это обеспечивает undo и аудит.

## 10. Требования к ИИ-редактору

Основная модель — `bitrixgpt-5.5`, резервный вариант — `model: "auto"`.

Модели доступны инструменты:

| Инструмент | Назначение |
|---|---|
| `get_dashboard()` | Получить текущую спеку и версию |
| `list_entities()` | Получить разрешённые сущности |
| `get_entity_fields(entity)` | Получить реальные поля сущности |
| `preview_aggregate(query)` | Проверить будущую агрегацию до изменения спеки |
| `apply_changes(patch[])` | Применить JSON Patch после серверной валидации и создать версию |
| `revert(version)` | Откатиться к выбранной версии |

Ограничители:

- Модель меняет только спеку.
- Инструменты записи в CRM и задачи модели не выдаются.
- Произвольные запросы к API запрещены.
- В контекст модели передаются метаданные и агрегаты, без карточек клиентов и сырых персональных данных.
- Каждый патч проходит серверную валидацию.
- При ошибке модель получает результат проверки и может повторить попытку ограниченное число раз.
- Чат объясняет diff человеческим языком.
- Системный промпт требует сначала выполнить preview, затем apply, использовать реальные поля и отвечать коротко.

## 11. Безопасность

| Область | Требование |
|---|---|
| Скоупы Битрикс24 | Минимально необходимые `crm`, `task` + `tasks`, `user`, `placement` |
| Скоупы Вайбкода | `vibe:ai`, `vibe:infra`, при необходимости `vibe:storage` |
| Ключи | `vibe_app_...` хранится на BFF; отсутствует во фронтенде, репозитории, статье и скриншотах |
| Доступ | Авторизованные пользователи портала; редактирование владельцем |
| ИИ | BitrixGPT в инфраструктуре Битрикс24, без передачи сторонним LLM-провайдерам |
| Промпты и логи | Только метаданные и агрегаты; обязательная проверка отсутствия сырых персональных данных |

## 12. Риски и открытые вопросы разработчика

| # | Вопрос или риск | Запланированное действие |
|---|---|---|
| 1 | Доступен ли `BI_ANALYTICS_MENU` | Проверить `/v1/placements/available`; подготовить обычную встройку как запасной вариант |
| 2 | `BI_ANALYTICS_MENU` не передаёт auth-контекст | Оценить собственную сессию BFF; при высокой стоимости выбрать обычную встройку |
| 3 | Качество function calling у BitrixGPT | Провести ранний спайк; резерв — `gpt-oss-120b` или строгий парсинг с повтором |
| 4 | Потолок 5000 записей | Период по умолчанию; при превышении показывать бейдж «по выборке» |
| 5 | Ограничения частоты запросов | Кэш, пакетная загрузка виджетов, debounce обновлений |
| 6 | Формулировка о приватности | Согласовать с продуктовой командой до публикации |
| 7 | Название агента: ИИ-агент, CoPilot или OpenClaw | Сверить актуальный нейминг перед публикацией |

## 13. Метрики готовности

Приложение:

- Изменение отчёта фразой выполняется целиком быстрее 30 секунд.
- Ответ ИИ приходит быстрее 15 секунд.
- Дашборд на портале с 1–2 тысячами сделок загружается быстрее 3 секунд при тёплом кэше.
- В логах ИИ нет сырых персональных данных.
- Undo работает после каждого шага демонстрации.

Статья:

- Три демонстрационных сценария воспроизводятся читателем с нуля.
- Статья отвечает, почему приложение не редактирует нативный BI и где обрабатываются данные.

## 14. Требования к статье и демонстрации

Рабочий заголовок: «BI-отчёты, которые можно менять словами: строим дашборд с ИИ-редактором на платформе Вайбкод».

Структура:

1. Что такое BI-конструктор и BI-отчёты Битрикс24.
2. Зачем бизнесу настраивать отчёты и почему ручная настройка сложна.
3. Что умеет ИИ-агент Битрикс24 и почему у него нет доступа к BI-отчётам.
4. Как Вайбкод помогает построить отдельное приложение внутри портала.
5. Как подготовить тестовые данные через seed-скрипт и batch API.
6. Как создать дашборд и изменить его через ИИ.
7. Итоги, ограничения, безопасность и ссылка на документацию.

Демо-сценарии:

1. Визуальная правка: горизонтальный график, фирменные цвета, перенос KPI наверх.
2. Правка логики: новые клиенты, исключение тестовой воронки, текущий квартал.
3. Новый запрос: просроченные задачи по отделам и динамика по неделям.
4. Для каждого сценария показываются фраза, diff, результат и работа undo.

Материалы для статьи:

- нативный BI на портале;
- кабинет Вайбкода с замазанным ключом;
- seed-промпт;
- дашборд до изменений;
- три пары «фраза → результат»;
- undo;
- настройки доступа Black Hole.

## 15. Зафиксированные ограничения API

- REST для BI ограничен семейством `biconnector.*`; API управления дашбордами отсутствует.
- `BI_ANALYTICS_MENU` использует scope `placement` и открывает handler без `AUTH_ID`, `member_id` и `PLACEMENT_OPTIONS`.
- Entity API поддерживает list/search/aggregate/batch/fields.
- Aggregate поддерживает `count`, `sum`, `avg`, `min`, `max`, до пяти полей `groupBy` и выборку до 5000 записей для числовых функций.
- Batch принимает до 500 операций.
- Действуют лимиты 10 rps на портал и 60 запросов в минуту на ключ по умолчанию.
- AI API расположен по адресу `/v1/ai/chat/completions`, совместим с OpenAI API, поддерживает streaming и function calling.
- Placements проверяются через `/v1/placements/available`, управляются через bind/unbind и требуют `vibe_app_...` со scope `placement`.
- Black Hole предоставляет серверы без публичного IP и доступ через туннель.

# Часть II. Архитектура и план реализации

## 16. Текущее состояние

В репозитории уже есть минимальный Node.js-прототип:

- сервер читает ключ из `.env`;
- `/api/me` проксирует запрос к Вайбкоду;
- интерфейс показывает статичный дашборд, поле команды и диагностику подключения;
- ключ остаётся на сервере.

Пока отсутствуют OAuth-приложение, реальные данные, JSON-спека, AI-вызовы, версии, хранилище, тесты и встройка в Битрикс24.

## 17. Предлагаемый стек

| Слой | Решение | Причина |
|---|---|---|
| Язык | TypeScript в браузере и на сервере | Общие типы спеки и проверяемые API-контракты |
| Frontend | React + Vite | Удобное состояние для набора виджетов, чата и undo |
| Графики | Apache ECharts | KPI, bar, line, pie/donut и адаптивные графики одной библиотекой |
| Backend/BFF | Node.js + Fastify | Небольшой HTTP-слой, схема запросов и удобное тестирование |
| Валидация | Zod | Одна схема для спеки, API и AI-патчей |
| Изменения спеки | RFC 6902 JSON Patch | Ограниченные и проверяемые правки от модели |
| Хранилище MVP | SQLite с адаптером репозитория | Быстрый локальный старт; способ постоянного хранения на Black Hole проверить до фиксации |
| Тесты | Vitest + Fastify inject + Playwright | Бизнес-логика, API и ключевой пользовательский сценарий |
| Качество | ESLint + Prettier + `tsc --noEmit` | Единый стиль и строгая типизация |

Перед переносом прототипа на этот стек нужно подтвердить поддержку Node.js и постоянного диска в целевой конфигурации Black Hole. При отсутствии постоянного диска хранилище переключается на Postgres или доступное хранилище Вайбкода.

## 19. Потоки работы приложения

### Открытие

1. Битрикс24 открывает приложение во встройке.
2. BFF проверяет OAuth-сессию и пользователя портала.
3. Frontend получает текущую спеку и права пользователя.
4. BFF преобразует виджеты в безопасные aggregate-запросы.
5. Вайбкод возвращает агрегаты, frontend строит графики.

### Изменение через чат

1. Пользователь пишет: «Покажи продажи по менеджерам горизонтально».
2. BFF передаёт модели текущую спеку, разрешённые инструменты и минимум метаданных.
3. Модель запрашивает поля и выполняет `preview_aggregate`, если меняется логика данных.
4. Модель вызывает `apply_changes` с JSON Patch.
5. Сервер проверяет версию, схему, поля, функции и права.
6. Сервер сохраняет новую полную версию спеки.
7. UI обновляет дашборд и показывает diff.

### Undo

1. Пользователь нажимает кнопку отката.
2. BFF создаёт новую версию на основе предыдущей валидной спеки.
3. UI получает обновлённый дашборд и показывает, что было возвращено.

## 20. Контракты BFF

Минимальный набор маршрутов:

| Метод и путь | Назначение |
|---|---|
| `GET /api/session` | Текущий пользователь, портал и роль |
| `GET /api/dashboard` | Актуальная спека и версия |
| `GET /api/dashboard/versions` | История версий без секретных данных |
| `POST /api/dashboard/revert` | Создать версию-откат |
| `POST /api/data/query` | Получить данные для разрешённых виджетов |
| `POST /api/data/refresh` | Сбросить кэш владельцем |
| `GET /api/metadata/entities` | Разрешённые сущности |
| `GET /api/metadata/:entity/fields` | Поля сущности |
| `POST /api/chat` | Выполнить AI tool loop и вернуть diff |
| `GET /api/diagnostics` | Санитизированные возможности платформы |

Frontend не передаёт произвольный URL или метод Вайбкода. BFF принимает только типизированные команды предметной области.

## 21. Хранение данных

Минимальные таблицы:

- `portals`: идентификатор портала и настройки.
- `users`: идентификатор пользователя портала и роль.
- `dashboards`: один дашборд MVP, владелец и номер актуальной версии.
- `dashboard_versions`: полная JSON-спека, автор, источник изменения, дата и краткий diff.
- `chat_messages`: сообщения без сырых CRM-записей и технические статусы tool calls.
- `sessions`: серверные пользовательские сессии с защищёнными cookie.

Кэш агрегатов хранится отдельно с ключом из портала, нормализованного запроса и версии периода. TTL по умолчанию — 5 минут.

## 22. Безопасность реализации

- Все env-переменные валидируются при старте; ключи не логируются.
- Cookie сессии: `HttpOnly`, `Secure`, `SameSite` с учётом iframe-сценария.
- Изменяющие маршруты защищаются от CSRF и проверяют роль владельца.
- В API-клиенте существует whitelist путей, сущностей, полей и функций.
- В AI-контекст не попадают сырые записи, телефоны, email и карточки клиентов.
- Логи содержат request ID, длительность и код ошибки, но не ключи, OAuth-токены и персональные данные.
- AI tool loop имеет лимит шагов, таймаут и ограниченный повтор после ошибки валидации.
- В `computed` используется небольшой интерпретатор разрешённых операций; `eval` и исполнение строк запрещены.

## 23. Поэтапный план

### Этап 0. Техническая разведка

Результат: подтверждены API и решения, от которых зависит архитектура.

Работы:

- проверить `/v1/placements/available` и наличие `BI_ANALYTICS_MENU`;

- проверить постоянное хранилище на Black Hole;

Критерий готовности: по каждому открытому вопросу есть сохранённый ответ API, решение и запасной вариант.

### Этап 1. Инженерный каркас

Результат: типизированное приложение запускается локально и проходит автоматические проверки.

Работы:

- перенести сервер и frontend на TypeScript;
- подключить Vite, React, Fastify, Zod, ESLint, Prettier и Vitest;
- добавить проверяемую конфигурацию env;

- определить общую Zod-схему спеки.

Проверки: typecheck, lint, unit-тесты схемы, production build.

### Этап 2. Seed и слой данных

Результат: тестовый портал заполнен воспроизводимыми данными, а приложение строит реальные агрегаты.

Работы:

- реализовать идемпотентный seed-скрипт с префиксом тестовых сущностей;
- добавить dry-run и явное подтверждение перед записью;
- реализовать клиент fields/statuses/aggregate;
- преобразовывать виджет спеки в разрешённый aggregate-запрос;
- добавить TTL-кэш, debounce и обработку лимитов;
- показать пустые состояния, ошибки и отметку выборки до 5000 записей.

Проверки: тест преобразования спеки в запрос, тест лимитов и кэша, ручная сверка нескольких агрегатов с порталом.

### Этап 3. Рендерер дашборда

Результат: все типы виджетов строятся из одной валидной спеки.

Работы:

- реализовать KPI, bar, line, pie/donut и таблицу;
- добавить общий период и переопределение на виджете;
- добавить загрузку, пустое состояние и ошибку каждого виджета;
- добавить ручное обновление;
- обеспечить адаптивную работу внутри iframe.

Проверки: unit-тесты преобразования данных, компонентные проверки виджетов, снимки desktop/mobile.

### Этап 4. Версии и undo

Результат: каждая правка сохраняется, история читается, откат безопасен.

Работы:

- создать миграции;
- реализовать append-only версии;
- добавить optimistic locking по номеру версии;
- реализовать diff и undo как создание новой версии;
- ограничить редактирование владельцем.

Проверки: конкурирующие правки, откат нескольких версий, отказ viewer-пользователю.

### Этап 5. AI-редактор

Результат: пользователь меняет дашборд фразой, сервер контролирует каждое действие модели.

Работы:

- подключить `/v1/ai/chat/completions`;
- реализовать инструменты `get_dashboard`, `list_entities`, `get_entity_fields`, `preview_aggregate`, `apply_changes`, `revert`;
- добавить системный промпт и правило preview-before-apply;
- валидировать JSON Patch и итоговую спеку;
- ограничить число шагов и повторов;
- вернуть в UI короткий diff и понятные ошибки.

Проверки: три демо-сценария, выдуманное поле, невалидная агрегация, попытка записи в CRM, конфликт версии, таймаут модели.

### Этап 6. OAuth, доступ и встройка

Результат: приложение безопасно открывается внутри тестового портала.

Работы:

- создать приложение с `vibe_app_...` и минимальными скоупами;
- реализовать OAuth callback и серверную сессию;
- проверить `BI_ANALYTICS_MENU`;
- при необходимости использовать обычную встройку;
- развернуть BFF и SPA на Black Hole;
- проверить права owner/viewer и отсутствие ключа во фронтенде.

Проверки: вход, истечение сессии, запрещённое редактирование, сетевые ошибки, просмотр bundle и логов на секреты.

### Этап 7. Полировка и материал для статьи

Результат: воспроизводимое демо и комплект иллюстраций.

Работы:

- пройти визуальную правку, правку логики и добавление нового виджета;
- измерить время загрузки и AI round-trip;
- проверить логи на персональные данные;
- снять пары «команда → diff → результат» и undo;
- зафиксировать ограничения и точные формулировки о приватности;
- обновить README инструкцией запуска и воспроизведения демо.

Критерий готовности: весь сценарий статьи проходит с чистого окружения по инструкции.

## 24. Порядок реализации

Работу следует вести последовательно:

1. Сначала закрыть техническую разведку, особенно placements, OAuth, entity API, BitrixGPT tools и хранилище.
2. Затем создать типизированный каркас и схему спеки.
3. После этого подключить реальные данные и рендер виджетов.
4. Далее добавить версии и undo.
5. На готовую безопасную модель изменений подключить AI-редактор.
6. После локальной готовности выполнить OAuth-встройку и деплой.
7. В финале провести демо, измерения и подготовить материалы статьи.

## 25. Ближайший шаг

Следующая задача — **Этап 0: техническая разведка**. Она должна дать короткий отчёт `docs/technical-discovery.md` с реальными ответами тестового портала и решениями по шести вопросам:

1. Placement для BI.
2. OAuth и пользовательская сессия.
3. Доступные сущности, поля, статусы и агрегаты.
4. Function calling BitrixGPT.
5. Постоянное хранилище Black Hole.
6. Наличие звонков в entity API.

До завершения этой проверки текущий интерфейс остаётся прототипом и не считается архитектурной основой MVP.
