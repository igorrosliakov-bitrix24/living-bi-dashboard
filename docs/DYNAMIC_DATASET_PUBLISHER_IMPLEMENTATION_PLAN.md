# План реализации динамического AI Dataset Publisher

**Дата:** 24.08.2026  
**Проект:** `living-bi-dashboard`  
**Статус:** этапы 1–8 реализованы и проверены на живом портале  
**Всего этапов:** 8

## 1. Цель

Реализовать минимальную версию AI Dataset Publisher, которая работает не с одной зашитой фразой, а с ограниченным набором комбинаций для CRM-сделок.

Пользователь описывает нужный набор данных обычным языком. BitrixGPT формирует структурированную спецификацию. Сервер проверяет её по каталогу разрешённых возможностей, показывает пользователю формулу, поля и фильтры, а после подтверждения создаёт или обновляет датасет через REST API Битрикс24.

Adapter хранит проверенную спецификацию, рассчитывает строки по актуальным данным портала и отдаёт их через четыре callback-маршрута BI-коннектора. Аналитик один раз вручную собирает нативный график. При следующих запросах BI-конструктор получает обновлённые строки без повторного создания графика.

Целевой пользовательский запрос:

> «Нужен набор данных — конверсия по менеджерам по неделям, без тестовой воронки».

## 2. Принцип минимальной реализации

Динамичность достигается комбинацией разрешённых элементов, а не генерацией произвольного SQL или JavaScript.

Первая версия поддерживает только:

- Сущность `crm.deal`.
- Безопасный каталог измерений, метрик, периодов и фильтров.
- Создание нового управляемого датасета.
- Совместимое добавление полей в существующий управляемый датасет.
- Создание версии `v2` при несовместимом изменении.
- Ручную сборку нативного графика в BI-конструкторе.

Первая версия не превращается в универсальный BI-конструктор и не получает доступ к конфигурации нативных графиков.

## 3. Текущее состояние, которое нужно сохранить

- Публичный HTTPS-adapter `living-bi-adapter-b24` работает на отдельном VibeCode-сервере.
- Четыре callback-маршрута BI-коннектора доступны Битрикс24.
- OAuth-приложение со scope `crm` и `biconnector` установлено.
- Датасет `vibecode_ai_deal_intake_weekly` опубликован и возвращает реальные строки.
- Нативная таблица по датасету сохранена.
- Нативный столбчатый график по неделям и менеджерам построен.
- Текущий датасет, его таблицу и график нельзя удалять или несовместимо изменять во время разработки новой версии.

Новая реализация создаёт отдельный датасет `vibecode_ai_deal_conversion_weekly` и не использует существующий датасет как полигон для миграций.

## 4. Целевая архитектура

```text
Текст пользователя
  -> BitrixGPT: prepare_dataset_spec
  -> серверная нормализация и проверка DatasetSpec
  -> preview формулы, полей, периода и фильтров
  -> подтверждение пользователя
  -> защищённая регистрация спецификации в adapter-е
  -> biconnector.dataset.add или biconnector.dataset.fields.update
  -> четыре callback-маршрута BI-коннектора
  -> расчёт строк по CRM портала
  -> нативный датасет и график Битрикс24
```

BitrixGPT не получает права выполнять REST-вызовы. Он выбирает только значения из серверного каталога. Все имена полей, типы, формулы и REST-параметры формирует сервер.

## 5. Поддерживаемая модель запросов

### 5.1. Измерения

| Ключ | Результирующие поля | Источник |
| --- | --- | --- |
| `week` | `WEEK_START` | Неделя по `BEGINDATE` сделки. |
| `manager` | `MANAGER_ID`, `MANAGER_NAME` | `ASSIGNED_BY_ID` и справочник пользователей. |
| `category` | `CATEGORY_ID`, `CATEGORY_NAME` | `CATEGORY_ID` и справочник воронок. |

В спецификации должно быть хотя бы одно измерение. Порядок измерений не влияет на вычисления, но сохраняется для preview.

### 5.2. Метрики

| Ключ | Поле | Тип | Формула |
| --- | --- | --- | --- |
| `total_deals` | `TOTAL_DEALS` | `integer` | Количество подходящих сделок. |
| `won_deals` | `WON_DEALS` | `integer` | Количество сделок с `STAGE_SEMANTIC_ID = "S"`. |
| `conversion_percent` | `CONVERSION_PERCENT` | `float` | `WON_DEALS / TOTAL_DEALS * 100`. |

Если выбран `conversion_percent`, сервер автоматически включает внутренний расчёт `total_deals` и `won_deals`. В результирующую схему попадают только метрики, которые пользователь запросил или подтвердил в preview.

При `TOTAL_DEALS = 0` конверсия равна `0`.

### 5.3. Периоды

- `current_month`.
- `current_quarter`.
- `current_year`.

Если пользователь не указал период, используется `current_quarter`. Границы периода показываются в preview.

### 5.4. Фильтры

- `excludeCategoryNames` — исключить до десяти воронок по названиям без учёта регистра.
- `includeCategoryNames` — оставить до десяти явно перечисленных воронок.

Одновременно использовать включение и исключение воронок нельзя. Неизвестное название воронки считается ошибкой preview, а не молча игнорируется.

### 5.5. Примеры запросов, которые обязаны работать

1. «Конверсия по менеджерам по неделям, без тестовой воронки».
2. «Количество всех и выигранных сделок по менеджерам за текущий квартал».
3. «Конверсия по неделям, исключи воронки Тест и Обучение».

Примеры должны создавать разные спецификации без добавления отдельных обработчиков для каждой фразы.

## 6. Контракт DatasetSpec

BitrixGPT возвращает только структуру следующего вида:

```json
{
  "entity": "crm.deal",
  "title": "Конверсия по менеджерам по неделям",
  "period": "current_quarter",
  "dimensions": ["week", "manager"],
  "metrics": ["total_deals", "won_deals", "conversion_percent"],
  "filters": {
    "excludeCategoryNames": ["Тест"]
  }
}
```

Сервер добавляет вычисляемые данные:

- Безопасное имя с префиксом `vibecode_ai_`.
- Версию спецификации.
- Итоговый список колонок.
- Типы колонок Битрикс24.
- Человекочитаемую формулу.
- Реальные границы периода.
- Diff относительно опубликованной версии.

### 6.1. Правила валидации

- `entity` допускает только `crm.deal`.
- Измерения, метрики и период должны присутствовать в каталоге возможностей.
- Дубликаты измерений и метрик запрещены.
- Должно быть хотя бы одно измерение и одна метрика.
- Названия воронок должны существовать в текущем портале.
- Название датасета формирует сервер, а не модель.
- Модель не может передать REST-метод, URL, SQL, JavaScript или произвольное имя CRM-поля.
- Длина заголовка, запроса и списков ограничивается на сервере.

## 7. Реестр спецификаций adapter-а

Путь постоянного состояния:

```text
/opt/data/state/dataset-specs.json
```

Для каждой таблицы хранятся:

- `schemaVersion`.
- `datasetName`.
- `title`.
- Проверенная `DatasetSpec`.
- Сгенерированный список полей.
- Статус `pending`, `active` или `failed`.
- Идентификатор датасета Битрикс24 после публикации.
- Время создания, обновления, последнего расчёта и последней выдачи данных.

Запись выполняется атомарно через временный файл и `rename`. Файл хранится с режимом `0600` и владельцем пользователя сервиса.

### 7.1. Публичные маршруты BI-коннектора

Сохраняются существующие маршруты:

- `POST /bi-connector/check`.
- `POST /bi-connector/tables`.
- `POST /bi-connector/table-description`.
- `POST /bi-connector/data`.

Они не требуют Gateway-сессии, потому что вызываются серверами Битрикс24.

### 7.2. Защищённые управляющие маршруты

Добавляются служебные маршруты, которые не регистрируются в BI-коннекторе:

- `POST /control/datasets` — подготовить, активировать или удалить спецификацию.
- `POST /control/refresh` — очистить кэш и пересчитать выбранный датасет.

Оба маршрута требуют `X-Adapter-Control-Key`. Значение ключа хранится только в защищённых переменных окружения dashboard и adapter-а.

## 8. Правила создания и обновления схемы

Перед публикацией сервер получает существующий датасет и его реальные поля, затем строит diff.

### 8.1. Совместимые изменения

- Добавление нового поля выполняется через `biconnector.dataset.fields.update` с параметром `add`.
- Изменение описания датасета выполняется через `biconnector.dataset.update`.
- Поле, которое больше не показывается в новой спецификации, можно скрыть через `visible: false`, сохранив его расчёт для старых графиков.

### 8.2. Несовместимые изменения

К несовместимым относятся:

- Переименование поля.
- Смена типа поля.
- Изменение смысла существующего поля при сохранении прежнего кода.
- Удаление поля, которое может использоваться сохранённым графиком.

Для них создаётся новый датасет с суффиксом `_v2`. Старый датасет и его графики сохраняются.

### 8.3. Порядок публикации

1. Сохранить спецификацию в adapter-е со статусом `pending`.
2. Создать или совместимо обновить датасет Битрикс24.
3. Сохранить полученный ID и перевести спецификацию в `active`.
4. При ошибке REST удалить только новую `pending`-запись и оставить предыдущую активную версию.

Реальное создание, обновление и удаление объектов портала выполняются только после отдельного подтверждения пользователя.

## 9. Интерфейс

### 9.1. Подготовка

Пользователь:

1. Выбирает «Создать новый набор» или один из управляемых датасетов для обновления.
2. Вводит запрос обычным языком.
3. Нажимает «Подготовить набор».

### 9.2. Preview

Интерфейс показывает:

- Название и техническое имя датасета.
- Источник `crm.deal`.
- Период и реальные даты.
- Измерения, метрики и итоговые поля.
- Формулу конверсии.
- Включённые или исключённые воронки.
- Пример строк без персональных данных.
- Diff при обновлении существующего набора.
- Предупреждение о создании `v2`, если изменение несовместимо.

### 9.3. Действия

В интерфейсе остаются только кнопки из продуктового запроса:

- «Опубликовать набор» или «Обновить набор».
- «Обновить данные».
- «Проверить синхронизацию».
- «Удалить набор».

Поле с ручным вводом `publish_dataset` удаляется. Публикация подтверждается диалогом с названием набора и перечнем изменений. Удаление подтверждается отдельным диалогом с техническим именем датасета.

Кнопка «Обновить данные» вызывает защищённый adapter endpoint, очищает кэш выбранного датасета, выполняет расчёт и показывает время завершения и количество агрегированных строк.

- Цепочка «текст → DatasetSpec → preview → подтверждение → Dataset API → adapter → нативный график» работает на живом портале.
- Сохранённый старый датасет и график продолжают работать.
- Новый график получает актуальные строки после принудительного обновления без пересоздания.

## 11. Обязательные тестовые сценарии

### 11.1. Happy path

Запрос про конверсию создаёт поля `WEEK_START`, `MANAGER_ID`, `MANAGER_NAME`, `TOTAL_DEALS`, `WON_DEALS` и `CONVERSION_PERCENT`.

### 11.2. Динамическая комбинация

Запрос только по менеджерам без недель создаёт схему без `WEEK_START`. Запрос только по неделям создаёт схему без менеджеров.

### 11.3. Фильтр воронок

Названия «Тест», «тест» и «ТЕСТ» соответствуют одной воронке. Неизвестное название останавливает preview с объяснением.

### 11.4. Совместимое обновление

Добавление `WON_DEALS` показывает diff и вызывает `biconnector.dataset.fields.update` только после подтверждения.

### 11.5. Несовместимое обновление

Попытка изменить тип `CONVERSION_PERCENT` создаёт предложение `_v2`. Исходный датасет не изменяется.

### 11.6. Ошибки инфраструктуры

Недоступный adapter, истёкший OAuth, нечитаемый state-файл и ошибка REST показываются отдельно и не превращаются в пустой датасет.

### 11.7. Безопасность

Неизвестный table, неправильный управляющий ключ, чужой датасет и имя без `vibecode_ai_` отклоняются.

## 12. Риски и меры

| Риск | Мера |
| --- | --- |
| Понятие конверсии неоднозначно. | Всегда показывать формулу и знаменатель в preview. |
| Изменение схемы ломает график. | Добавлять поля совместимо, для смены типа или смысла создавать `v2`. |
| BitrixGPT предлагает неподдерживаемое поле. | Проверять каждый ключ по серверному каталогу. |
| Публичный adapter получает управляющий запрос извне. | Требовать отдельный control key и не включать его в логи. |
| OAuth-файл теряет владельца после обслуживания. | Проверять чтение state в `/health` и владельца при деплое. |
| Расчёт большого периода выполняется долго. | Ограничить период, число сделок и использовать кэш на один датасет. |
| Частичная ошибка оставляет несогласованную схему. | Использовать статусы `pending` и `active`, откатывать только новую pending-запись. |
| Малое число выигранных сделок делает график неинформативным. | Проверять агрегаты в preview, не менять формулу ради красивой картинки. |

## 13. Что не входит в реализацию

- Произвольные SQL-запросы и формулы.
- Другие CRM-сущности, задачи и смарт-процессы.
- Автоматическое создание и редактирование нативных графиков.
- Фоновый планировщик обновлений.
- Полноценная история диалога с BitrixGPT.
- Один adapter для нескольких порталов.
- Редизайн всего приложения.
- Изменение существующего `vibecode_ai_deal_intake_weekly`.
- Изменение или удаление чужих коннекторов, источников, датасетов и отчётов.

Добавить read-only команду:

```bash

```

Она должна принимать проверенную спецификацию и показывать только итоговую схему, число исходных сделок, количество агрегированных строк и предупреждения. CRM-записи, токены и секреты не выводятся.
