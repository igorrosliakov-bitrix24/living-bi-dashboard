## Первый шаг при продолжении

1. Обновить страницу приложения в тестовом портале.
2. Ввести в поле «Команда для ИИ»: `Отсортируй стадии сделок по возрастанию`.
3. Нажать «Подготовить изменение», проверить понятный черновик, затем «Применить предложение».
4. Убедиться, что появилась новая версия и работает откат.

Это обязательная живая проверка function calling BitrixGPT. Код и контракт инструмента покрыты тестами, но после последнего деплоя сценарий ещё не подтверждён в iframe портала.

## Что осталось по PRD

1. Доработать отображение виджетов `line`, `pie`, `donut` и `table`: типы уже разрешены в JSON-спеке, но интерфейс пока рисует KPI и bar.
2. Добавить безопасные вычисляемые KPI (`computed`) без исполнения произвольного кода.
3. Подключить `/v1/statuses` и показывать понятные названия стадий сделок вместо технических идентификаторов.
4. Показать пользователю ограничение агрегатов в 5000 записей.
5. Расширить seed-данные: стадии и даты сделок на интервале 6–12 месяцев, дедлайны и просрочку задач. Скрипт существует, но его стоит сверить с этим набором перед демонстрацией.
6. Обновить `docs/technical-discovery.md`, README и матрицу соответствия PRD после закрытия пунктов выше.

## Важные ограничения для статьи

- Приложение не читает и не редактирует нативные BI-отчёты: доступного REST API для этого нет.
- Это отдельный дашборд на данных того же портала, расположенный рядом с BI-конструктором.
- Для BitrixGPT корректная формулировка: данные не передаются сторонним LLM-провайдерам; обработка идёт в инфраструктуре Битрикс24 и Вайбкода. Нельзя писать, что данные вообще не покидают портал.
