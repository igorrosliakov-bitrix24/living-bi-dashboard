### Ограничение тестовых данных `b24-w9apyi` (23.08.2026)

Датасет отдал всего две строки. Причина не в адаптере, а в данных портала: из 2028 сделок текущего квартала **2024 помечены как повторные** (`isReturning: true`) и только 4 — новые. Рецепт `manager_weekly_new_deals` по определению считает `IS_RETURN_CUSTOMER === "N"`, поэтому почти всё отсекается.

### Набор новых сделок и перевод рецепта на BEGINDATE (23.08.2026)

Рецепт `manager_weekly_new_deals` переведён с `DATE_CREATE` на `BEGINDATE`: в Битрикс24 `createdAt` доступен только для чтения, поэтому сделку задним числом создать нельзя и весь набор ложился в одну неделю. Поле «Дата начала» записывается свободно. В группировке оставлен запасной вариант `BEGINDATE || DATE_CREATE`, чтобы сделки без даты начала не выпадали из расчёта.

**Важно:** изменение затрагивает и живой датасет на `chepyuk`, где `BEGINDATE` и дата создания у реальных сделок расходятся. Адаптер `living-bi-dataset-adapter` намеренно **не передеплоивался** и продолжает работать на прежнем расчёте. Обновлять его — отдельным решением.

Добавлен seed новых сделок: [lib/intake-seed.js](../lib/intake-seed.js), [scripts/seed-intake-data.js](../scripts/seed-intake-data.js), тесты в [test/intake-seed.test.js](../test/intake-seed.test.js), команда `npm run seed:intake`. Пространство имён `VIBECODE_INTAKE_BI` отделено от `VIBECODE_DEMO_BI` и `VIBECODE_LOAD_BI`.

#### Поведение признака «повторная сделка», выясненное опытом

Битрикс24 **пересчитывает `IS_RETURN_CUSTOMER` фоново**, уже после создания записи. Значение, переданное в `crm.deal.add`, сразу после ответа выглядит сохранённым, а через десятки секунд заменяется расчётным. Проверять признак немедленно после записи бесполезно — нужен интервал около минуты.

Правило пересчёта подтверждено тремя пробами:

| Клиент сделки | Итоговый признак |
| --- | --- |
| клиента нет | новая |
| своя компания без других сделок | новая |
| компания, у которой уже есть сделки | повторная |

Отсюда провал первого прогона: 360 сделок разложили на восемь общих компаний, и всё, кроме первой сделки каждой компании, стало повторным. В датасет попадало две строки.

Исправлено двумя изменениями. Seed теперь создаёт отдельного клиента под каждую сделку. Для уже созданных записей добавлен режим `npm run seed:intake -- --repair --confirm`: он снимает клиента и признак повторности через batch-обновление. Batch API требует `entityId` рядом с `params`, а не `id` внутри — иначе `MISSING_ENTITY_ID`.

### Раскладка дат нагрузочного набора (24.08.2026)

Все 2000 сделок `VIBECODE_LOAD_BI` имели `BEGINDATE` равной дате создания и попадали в одну неделю `2026-08-10`. Поскольку рецепт конверсии не исключает повторные сделки, эта неделя показывала 2079 сделок против ~51 в остальных.

В seed добавлен режим обслуживания `npm run seed:intake -- --spread --namespace=VIBECODE_LOAD_BI --weeks=8 --confirm`. Он раскладывает `BEGINDATE` по неделям текущего квартала batch-обновлением, не создавая записей. Даты ограничены сегодняшним днём: в будущее сделки не уезжают. Пространство имён валидируется шаблоном `VIBECODE_[A-Z_]+`, чтобы нельзя было задеть чужие записи.

Результат: 8 недель по ~300 сделок, всего 2391, общая конверсия 25%. Датасет новых сделок не затронут — он исключает повторные, и там по-прежнему 7 недель и 368 сделок.

**Осталось решить для статьи.** Недельная конверсия получилась не ровной, а с двумя одинаковыми пиками: 46,2% в неделю `07-06` и 46,8% в неделю `08-03` против 14-22% в остальных. Это артефакт арифметики, а не поведение данных: стадия сделки в нагрузочном seed назначается как `index % 4`, а неделя при раскладке — как `index % 8`. Восьмёрка кратна четвёрке, поэтому номер недели и стадия скоррелированы. Читатель статьи прочтёт эти пики как деловой сигнал. Варианты: разложить на число недель, взаимно простое с четвёркой (например 7), либо перемешать назначение недель детерминированным сдвигом.

## Важные ограничения для статьи

- Приложение не читает и не редактирует готовые нативные BI-отчёты. REST API Битрикс24 позволяет создавать собственные датасеты, доступные нативному BI-конструктору; это подтверждено живым прогоном. Возможность чтения и изменения конфигурации отчётов, включая графики, фильтры и раскладку, не подтверждена изученными методами.
- Для прямой работы с датасетами требуется OAuth-авторизация локального приложения Битрикс24 со scope `biconnector`. Интерфейс дашборда пока использует Gateway и API Вайбкода.
- Это отдельный дашборд на данных того же портала, расположенный рядом с BI-конструктором.
- Корректная формулировка: данные не передаются сторонним LLM-провайдерам; обработка идёт в инфраструктуре Битрикс24 и Вайбкода.
