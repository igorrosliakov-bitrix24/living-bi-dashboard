# Ошибки и предотвращение повторов: памятка для агентов

## Контекст

Проект объединяет основной интерфейс AI-редактора, OAuth-приложения Битрикс24, публичные VibeCode-adapter-ы и BI Dataset API. В истории есть два портала: `chepyuk.bitrix24.ru` и `b24-w9apyi.bitrix24.ru`. Их нельзя считать одним контуром.

## Ошибка 1. Смешение привязки приложения, сервера и портала

**Симптом:** код выложен, но пользователь не видит пункт приложения в нужном портале или получает «приложение не обнаружено».

**Причина:** предположение, что сервер VibeCode автоматически устанавливает или переносит приложение между порталами.

**Правило:** до деплоя зафиксировать в `PROGRESS.md` таблицу:

| Компонент | Значение |
| --- | --- |
| Портал | точный домен |
| Основное приложение | название, placement ID, сервер и URL |
| OAuth-приложение | портал и scopes |
| Adapter | сервер и публичный HTTPS URL |
| BI-объекты | префикс, владелец и назначение |

После выкладки отдельно проверить: public URL, запуск placement в портале, OAuth callback и adapter `/health`.

## Ошибка 2. Смешение доказательств из разных порталов

**Симптом:** фраза «сценарий готов» относится к разным частям системы в разных порталах.

**Правило:** сообщать статус по уровням и порталам:

1. интерфейс доступен;
2. recipe/preview работает;
3. OAuth adapter готов;
4. датасет опубликован;
5. нативный BI получил строки;
6. график сохранён.

Не переносить статус одного портала на другой. В handoff явно указывать, какой контур подтверждён.

## Ошибка 3. Повторные deploy при `EXEC_BUSY`

**Симптом:** VibeCode принимает первую операцию, public URL даёт `502/503`, повторные вызовы возвращают `EXEC_BUSY`.

**Причина:** зависшая системная операция runtime/deploy-агента, например установка Node.js через пакетный менеджер.

**Правило диагностики:**

1. Считать статус операции, runtime и последние логи.
2. Проверить, создан ли platform service и достигнут ли healthcheck.
3. Выполнить предусмотренное VibeCode снятие блокировки максимум один раз.
4. Повторить проверку.
5. Если тот же симптом повторился, не отправлять новые deploy. Зафиксировать server ID, время, ответ API и фрагмент журнала; эскалировать в VibeCode или пересоздать сервер по согласованию.

## Ошибка 4. Неправильная модель сетевого доступа

**Факт:** BI Connector Битрикс24 вызывает adapter извне, поэтому нужен публичный HTTPS endpoint.

**Правило:** для обычного adapter-а предпочесть `PUBLIC` HTTPS. `OPEN` и SSH не являются условием работы BI и должны включаться только при отдельной технической потребности и согласовании.

В Black Hole прямой SSH может отсутствовать. Пользуйтесь Deploy API и журналами платформы. Deploy API очищает каталог приложения: OAuth-state, журнал синхронизации и статус нужно хранить в постоянном data directory за пределами `/opt/app`.

## Ошибка 5. Несоответствие тестовых данных рецепту

**Симптом:** запрос adapter-а успешен, но в датасете две-три строки и график малоинформативен.

**Причина:** данные не проходят фильтр рецепта; в нашем случае почти все сделки стали повторными, а recipe выбирает только новые.

**Правило:** перед скриншотами выполнить read-only контроль:

- число записей до фильтров;
- число записей после каждого фильтра;
- число агрегированных строк;
- наличие хотя бы нескольких менеджеров, недель и валют, если они нужны на графике.

Добавление CRM-данных — отдельное внешнее изменение, требующее подтверждения. Не ослаблять продуктовый расчёт ради красивого результата.

## Ошибка 6. Поздняя передача ручных действий пользователю

**Правило:** сразу передавать пользователю действия, которые проще выполнить в UI: создание API-ключа, перепривязка портала, выбор 2FA, отключение автосна, выбор тарифа и подтверждение OAuth. Давать ровно один следующий шаг и проверять результат после него. Не просить пользователя выполнять опасное действие без объяснения цели и области изменений.

## Ошибка 7. Нечёткие границы этапов UI

**Правило:** обозначать внешнее состояние в интерфейсе:

- preview — только схема, объектов в портале нет;
- подтверждённый черновик — ещё нет объекта в портале;
- публикация — создаёт или обновляет только согласованные технические объекты;
- кнопка проверки синхронизации появляется и имеет смысл после публикации.

Запрашивать отдельное явное подтверждение непосредственно перед публикацией или удалением.

## Ошибка 8. Несвоевременное обновление handoff-документов

**Правило:** после каждой развилки с порталом, сервером, OAuth или деплоем сразу обновлять `docs/PROGRESS.md` и `docs/CHAT_HANDOFF.md`. Новая актуальная запись должна стоять выше истории. Старое состояние помечать как «устаревшее», а не удалять, если оно объясняет принятые решения.

## Ошибка 9. Частичный архив заменил приложение Galaxy

**Симптом:** после небольшой правки dashboard перестал запускаться; журнал показывает отсутствие `/opt/app/package.json`.

**Причина:** в `POST /deploy` для существующего `GALAXY_APP` был отправлен архив только с изменёнными файлами. Агент ошибочно предположил merge, но Galaxy собрал контейнер из содержимого этого архива и заменил прежний код.

**Правило:**

1. Перед deploy прочитать карточку сервера и проверить `kind` и `createdVia`.
2. Для `GALAXY_APP` передавать полный самодостаточный архив приложения: `package.json`, точку запуска, все импортируемые локальные модули и статические файлы.
3. До отправки вывести безопасный список файлов архива и проверить наличие runtime-файлов. `.env`, ключи, `.git`, `node_modules` и результаты тестов в архив не включать.
4. Не считать multipart-deploy частичным обновлением Galaxy. Для одного файла использовать `/upload` только после проверки его контракта на этом сервере.
5. Ошибки `ENOENT` и `MODULE_NOT_FOUND` после deploy сначала трактовать как дефект архива. Восстановить тот же сервер полной сохранённой версией или полным архивом, не создавая новый сервер и не затрагивая BI-объекты.
6. Только если полный корректный архив доказан, а серверная операция действительно зависла по журналам, применять правила `EXEC_BUSY` из ошибки 3.

## Минимальный preflight перед реальной публикацией

1. Проверить точный портал, placement и server URL.
2. Проверить `/health`: `ok`, готовая OAuth-конфигурация, отсутствие последней ошибки синхронизации.
3. Проверить, что adapter доступен через public HTTPS.
4. Проверить, что имена датасета и полей проходят правила платформы.
5. Проверить preview и подтвердить черновик без внешних изменений.
6. Получить явное разрешение на конкретную публикацию.
7. После публикации проверить синхронизацию, строки и нативный BI-предпросмотр.
