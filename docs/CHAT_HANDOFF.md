Проект состоит из двух связанных, но разных направлений.

### 1. Собственный AI-дашборд

Это отдельное приложение, встроенное в портал Битрикс24 через Вайбкод-платформу. Оно читает данные CRM и показывает свой дашборд. Пользователь может менять поддерживаемые настройки: группировку, ориентацию графика, палитру, период и название. Изменения проходят через preview, применяются после подтверждения и сохраняются как версии с возможностью отката.

BitrixGPT может предложить структурированный патч только в границах заранее реализованной модели дашборда. Когда запрос требует новой бизнес-логики или нового типа виджета, интерфейс должен сформировать структурированную заявку для агента-разработчика.

Приложение готовит данные, а конфигурацию нативного графика собирает аналитик Битрикс24 через REST. В статье нельзя писать, что текущий дашборд редактирует существующие нативные BI-отчёты.

### 2. Публикация расчётного датасета в нативный BI-конструктор

Новый API Битрикс24 для BI Connector позволяет создать и изменить датасет: его имя, состав колонок и внешний источник данных. Битрикс24 запрашивает строки у публичного Adapter-сервера, а затем аналитик собирает график и дашборд в нативном BI-конструкторе.

Это подтверждённый рабочий путь для второй статьи: ИИ подготавливает полезный расчётный набор данных, а аналитик один раз задаёт визуализацию в BI-конструкторе.

## Что уже доказано на практике

### Собственный дашборд

На исходном тестовом портале `b24-w9apyi.bitrix24.ru` работает приложение «AI-редактор BI-отчётов». Для него подготовлены тестовые CRM-данные, включая нагрузочный набор примерно из двух тысяч сделок и тестовых менеджеров.

Визуальный запрос вида «сделай график по менеджерам горизонтальным и в цветах бренда, KPI-карточки подними наверх» выполняется только для тех настроек, которые уже присутствуют в модели приложения. Сохранение версии фиксирует настройки и обновляет график. Параметры, которых в модели нет, не должны молча считаться выполненными.

Сценарии со сложной бизнес-логикой или новым виджетом в текущей реализации переходят в «заявку на доработку»: BitrixGPT описывает недостающие данные, правила, критерии готовности и ограничения для внешнего агента-разработчика.

### Нативный BI-конструктор и Dataset API

На общем портале `chepyuk.bitrix24.ru` создан и проверен расчётный датасет:

```text
vibecode_ai_deal_intake_weekly
```

Он получает реальные CRM-данные и возвращает агрегацию новых сделок за текущий квартал по неделям и менеджерам. Тестовые воронки и повторные сделки исключены правилами расчёта.

Проверенная схема датасета:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `WEEK_START` | date | начало недели |
| `MANAGER_ID` | integer | идентификатор менеджера |
| `MANAGER_NAME` | string | имя менеджера |
| `CURRENCY_ID` | string | валюта сделки |
| `NEW_DEALS` | integer | количество новых сделок |
| `PIPELINE_AMOUNT` | float | сумма сделок |
| `AVERAGE_AMOUNT` | float | средняя сумма |
| `WEEKLY_SHARE_PERCENT` | float | доля недели в процентах |

Через нативный интерфейс Битрикс24 было вручную сделано следующее:

1. Открыта таблица `vibecode_ai_deal_intake_weekly` и подтверждён предпросмотр реальных строк.
2. Создан график «Новые сделки по менеджерам по неделям»: ось X — `WEEK_START` с шагом «Неделя», мера — `SUM(NEW_DEALS)`, измерение — `MANAGER_NAME`.
3. Создан нативный дашборд «VibeCode AI — тест датасета», график размещён на нём и сохранён.

Итог: цепочка «CRM портала -> Adapter -> BI Connector -> нативный датасет -> нативный график -> нативный дашборд» работает.

## Почему это важно

Нативный BI-конструктор уже содержит системные наборы сделок, лидов и задач. Повторная публикация таких же сырых данных не создаёт ценности. Польза Dataset API появляется, когда приложение публикует расчётный слой:

- новую метрику, например конверсию или скорость прохождения стадий;
- данные из внешней системы, например ERP или 1С;
- объединённый набор, в котором CRM связана с внешними данными.

Новый расчётный датасет позволяет аналитику собрать график один раз. Дальше Битрикс24 обращается к Adapter-источнику за актуальными строками, поэтому данные в графике обновляются без ручной выгрузки.

## Архитектура и термины

### Gateway и BFF

Gateway Вайбкод-платформы открывает приложение внутри Битрикс24 и передаёт серверу контекст пользователя. В модели BFF (Backend for Frontend, серверный слой между интерфейсом и внешними API) браузер показывает интерфейс, а ключ приложения и пользовательские токены остаются на сервере.

Текущие серверные сессии нельзя считать окончательным production-решением: для деплоя понадобится постоянное защищённое хранилище сессий, журналирование и политика их очистки.

### Adapter и Connector

Adapter — публичный HTTPS-сервер нашего приложения. Битрикс24 обращается к нему за списком таблиц, описанием полей и строками данных.

Connector — зарегистрированная в Битрикс24 связка с этим Adapter-сервером. Он позволяет BI-конструктору видеть внешний источник как датасет.

Для Adapter используются четыре точки входа: проверка доступности, список таблиц, схема таблицы и выдача строк. Публичный HTTPS обязателен: Битрикс24 сам выполняет запросы к Adapter, локальный `localhost` ему недоступен.

## Важные ограничения API

Dataset API даёт возможность создавать и обновлять датасеты. Тип визуализации, оси, фильтры, вычисляемые поля и раскладку на дашборде выбирает аналитик в BI-конструкторе.

Поэтому рабочее разделение такое:

1. ИИ и приложение готовят расчётный набор: название, поля, типы, правила расчёта и источник.
2. Сервер валидирует схему и публикует её после подтверждения пользователя.
3. Аналитик вручную собирает первый график и размещает его на нативном дашборде.

Ограничения имён необходимо валидировать на сервере:

| Сущность | Правило |
| --- | --- |
| Имя датасета | строчная латинская буква в начале, далее строчные латинские буквы, цифры и `_`; максимум 230 символов |
| Имя поля | заглавная латинская буква в начале; максимум 32 символа |
| Тип поля | integer, string, float, date или datetime |

## Безопасные границы для общего портала

Работа ведётся на `chepyuk.bitrix24.ru`, где есть данные других людей. Перед любым действием соблюдать следующие правила.

1. Создавать только тестовые BI-объекты с префиксом `vibecode_ai_`.
2. Не изменять CRM-записи, существующие отчёты, настройки ролей, приложения и чужие дашборды без отдельного подтверждения пользователя.
3. Не удалять текущий датасет `vibecode_ai_deal_intake_weekly`, созданный нативный график или дашборд «VibeCode AI — тест датасета».

В тестах и документации нельзя сохранять реальные карточки, телефоны, email, ключи, токены или webhook URL. При необходимости использовать только агрегированные данные и безопасные заглушки.

## Локальное OAuth-приложение и доступ

Для Dataset API требуется локальное OAuth-приложение Битрикс24 со scope `biconnector`. Одного входящего webhook недостаточно: методы работают в контексте приложения.

На общем портале локальное приложение уже создано и получило доступ к CRM и BI Connector. Пользователь добавил себя в роль «Аналитик» в правах BI-конструктора. При сбоях встречались две категории проблем:

- доступ закрыт или кнопка входа возвращает отказ в доступе;
- `ChunkLoadError` в нативном интерфейсе BI-конструктора.

Такие ошибки относились к авторизации, ролям или кэшу фронтенда Битрикс24, а не к данным датасета. Практический порядок проверки: открыть BI-конструктор внутри авторизованного портала, проверить роль «Аналитик», обновить страницу с очисткой кэша или открыть свежую вкладку, затем повторить действие.
