# План проекта: ИИ готовит датасеты для BI-конструктора Битрикс24

**Статус:** REST-эксперимент завершён; реализованы UI-черновик, безопасный BitrixGPT Planner и отдельный путь публикации с typed-confirmation. Живой вызов публикации из UI ещё не выполнялся.  
**Рабочее название:** AI Dataset Publisher.  
**Цель первой версии:** пользователь описывает нужный расчёт обычной фразой, BitrixGPT готовит безопасный рецепт набора данных, приложение публикует датасет в «Рабочее место аналитика», а аналитик один раз собирает по нему нативный график.

## 1. Что уже подтверждено

В текущем репозитории работает технический прототип полной цепочки:

1. Локальное приложение Битрикс24 вызывает REST API со scope `biconnector`.
2. Скрипт создаёт коннектор, источник и датасет.
3. BI-конструктор обращается к adapter-сервису и получает строки данных.
4. Аналитик создаёт нативный график и размещает его на дашборде.

Тест с тремя демонстрационными сделками прошёл end-to-end. Следующий проект превращает этот прототип в понятный пользовательский сценарий с BitrixGPT, проверками, постоянным хранением и интерфейсом управления.

## 2. Идея продукта простыми словами

Аналитик обычно выполняет две разные работы. Сначала он готовит данные: выбирает источники, задаёт фильтры и рассчитывает показатели. Затем он настраивает представление: выбирает график, указывает оси и размещает виджет на дашборде.

В новом проекте BitrixGPT берёт на себя подготовку данных. Пользователь пишет, например:

> Нужен набор данных: конверсия по менеджерам по неделям, без воронки «Тест», за текущий квартал.

ИИ формирует описание расчёта и колонок. Сервер проверяет его, показывает пользователю preview и после подтверждения публикует датасет через REST API Битрикс24. Аналитик открывает этот датасет в BI-конструкторе, выбирает подходящий график и сохраняет его.

Дальше BI-конструктор запрашивает актуальные строки у adapter-сервиса. Ручная настройка графика сохраняется, а данные в нём обновляются через опубликованный источник.

## 3. Первый бизнес-сценарий

Для первой версии используем пример компании по производству окон. Руководителю отдела продаж нужна недельная конверсия новых клиентов по менеджерам за текущий квартал. Воронка «Тест» в расчёт не входит.

Датасет содержит шесть полей:

| Поле | Тип | Смысл |
|---|---|---|
| `WEEK_START` | `date` | Начало недели. |
| `MANAGER_ID` | `int` | Идентификатор менеджера. |
| `MANAGER_NAME` | `string` | Имя менеджера для подписи графика. |
| `NEW_CLIENTS` | `int` | Число новых клиентов. |
| `WON_CLIENTS` | `int` | Число клиентов с успешной сделкой. |
| `CONVERSION_RATE` | `double` | Конверсия в процентах. |

В первой версии приложение поддерживает этот расчёт как проверяемый шаблон. BitrixGPT заполняет параметры шаблона, но не создаёт произвольный код или SQL.

## 4. Пользовательский путь

```text
Фраза пользователя
        ↓
BitrixGPT готовит рецепт датасета
        ↓
Сервер проверяет поля, фильтры и расчёты
        ↓
Preview: схема, пример строк и diff
        ↓
Пользователь подтверждает публикацию
        ↓
REST API создаёт датасет в Битрикс24
        ↓
BI-конструктор запрашивает строки у adapter-сервиса
        ↓
Аналитик один раз создаёт график вручную
        ↓
График сохраняется, данные обновляются через adapter
```

## 5. Граница возможностей

Приложение автоматизирует подготовку набора данных: его схему, описание, фильтры и разрешённые расчёты. REST API позволяет создать датасет, изменить его описание, добавить или скрыть поля и удалить датасет.

Тип графика, оси, визуальные фильтры и расположение виджетов аналитик настраивает в нативном BI-конструкторе. Изученные методы `biconnector.*` не дают приложению API для управления этой частью отчёта.

Первая версия также не включает подключение 1С, произвольные объединения источников и генерацию исполняемого кода. Эти возможности можно добавлять отдельными проверяемыми шаблонами после MVP.

## 6. Архитектура

### 6.1. Интерфейс приложения

В существующем приложении появляется раздел «Наборы данных». Он содержит поле команды, preview будущего набора, diff, статус публикации и действия «Опубликовать», «Проверить данные» и «Удалить».

Интерфейс показывает ссылку или короткую инструкцию для перехода в «Рабочее место аналитика». Время последнего обращения BI-конструктора к adapter-сервису выводится как «Последняя синхронизация».

### 6.2. BitrixGPT Planner

BitrixGPT получает текст пользователя и каталог разрешённых шаблонов. В ответ модель возвращает структурированный черновик, а не код.

Пример внутреннего рецепта:

```json
{
  "template": "manager_weekly_conversion",
  "title": "Конверсия новых клиентов по менеджерам",
  "period": "current_quarter",
  "filters": {
    "excludeCategoryNames": ["Тест"],
    "isReturning": false
  },
  "dimensions": ["weekStart", "managerId", "managerName"],
  "measures": ["newClients", "wonClients", "conversionRate"]
}
```

### 6.3. Валидатор рецептов

Сервер проверяет рецепт до обращения к данным и REST API. Разрешены только известные шаблоны, поля, периоды, фильтры и формулы. Названия датасетов и полей приводятся к требованиям Битрикс24.

Результат проверки содержит понятные ошибки. Например, сервер сообщит, что воронка не найдена или запрошенное измерение пока не поддерживается.

### 6.4. Исполнитель рецептов

Исполнитель получает данные портала, группирует их по неделям и менеджерам и рассчитывает конверсию. Для первого сценария он работает с CRM и справочником пользователей.

Adapter отдаёт BI-конструктору только колонки опубликованного датасета. В контекст BitrixGPT передаются схема, агрегаты и технические сообщения без содержимого карточек клиентов.

### 6.5. Сервис публикации

Сервис публикации управляет объектами Битрикс24:

1. Один коннектор на установленное приложение.
2. Один источник на портал и выбранный способ авторизации.
3. Отдельный датасет для каждого подтверждённого рецепта.

Для создания используются `biconnector.connector.add`, `biconnector.source.add` и `biconnector.dataset.add`. Для изменений применяются `biconnector.dataset.update` и `biconnector.dataset.fields.update`. Получение статуса и удаление выполняются через методы `get`, `list` и `delete`.

### 6.6. OAuth и хранение состояния

Product-контур использует локальное приложение Битрикс24 с OAuth. Сервер хранит access token, refresh token, идентификаторы коннектора, источника и датасетов.

Токены шифруются ключом из переменной окружения. Запись состояния выполняется атомарно на постоянный диск. Для MVP допускается один портал на одно развёртывание; многопортальная схема остаётся отдельной задачей.

### 6.7. Публичный adapter

Битрикс24 обращается к adapter-сервису самостоятельно, поэтому callback должен иметь постоянный публичный HTTPS-адрес. Gateway Вайбкода предназначен для пользовательского входа в приложение и не подходит для фонового запроса BI-конструктора, если внешний вызов требует Gateway-сессию.

Adapter реализует четыре точки входа: проверку доступности, список таблиц, описание полей и выдачу строк. Каждый запрос проходит аутентификацию, ограничение размера и безопасное журналирование без токенов и персональных данных.

## 7. Структура модулей

Новые модули можно добавить в текущий репозиторий без переписывания готового дашборда:

```text
lib/datasets/
  recipe-schema.js       # Runtime-валидация рецепта.
  recipe-planner.js      # Запрос к BitrixGPT и разбор tool call.
  recipe-diff.js         # Понятный diff для preview.
  recipe-executor.js     # Расчёт строк по шаблону.
  dataset-naming.js      # Имена по правилам Битрикс24.
  dataset-publisher.js   # Создание и обновление через REST.
  dataset-store.js       # Рецепты, версии, REST-id и статусы.
  oauth-store.js         # Зашифрованные OAuth-токены.

test/datasets/
  *.test.js
```

Проект остаётся на JavaScript ESM и получает строгую runtime-валидацию на всех внешних границах. Это сохраняет текущий стек и выполняет требование типобезопасности без смешивания JavaScript и TypeScript в одном небольшом сервере.

## 8. План реализации: 12 этапов

### Этап 1/12. Зафиксировать контракт MVP

**Разработка:** описать первый шаблон `manager_weekly_conversion`, формулу конверсии, поля и правила периода. Зафиксировать данные, которые получает BitrixGPT, и данные, которые остаются только на сервере.

**Что делает пользователь руками:** подтверждает бизнес-определение «нового клиента» и «успешной сделки». Также сообщает точное название тестовой воронки, которую нужно исключать.

**Проверка:** ручной расчёт на небольшой выборке совпадает с ожидаемым результатом.

**Критерий готовности:** одно и то же условие можно однозначно посчитать без догадок модели.

### Этап 2/12. Подготовить постоянный публичный HTTPS-адрес

**Разработка:** упаковать adapter в Docker или systemd-сервис, добавить `/health`, тайм-ауты и проверку конфигурации. Настроить безопасный секрет для callback.

**Что делает пользователь руками:** выбирает хостинг, на котором разрешены входящие HTTPS-запросы, и создаёт приложение или сервер. При необходимости привязывает домен. Подойдёт постоянный адрес провайдера, собственный домен покупать необязательно.

**Проверка:** `GET /health` доступен из интернета, а четыре callback-маршрута отвечают только на корректно подписанные запросы.

**Критерий готовности:** Битрикс24 может вызвать adapter без браузера и Gateway-сессии.

### Этап 3/12. Создать и установить локальное приложение Битрикс24

**Разработка:** подготовить install handler, OAuth callback, хранение портала и проверку прав. Для первого сценария нужны scope `biconnector`, `crm` и минимальный доступ к пользователям для подписей менеджеров.

**Что делает пользователь руками:** в разделе «Разработчикам» создаёт локальное серверное приложение, вставляет два публичных URL, выбирает права и нажимает «Сохранить» или «Установить». Затем подтверждает запрошенный доступ от имени пользователя, который видит «Рабочее место аналитика».

**Проверка:** сервер получает installation auth, сохраняет портал и выполняет `biconnector.dataset.list`.

**Критерий готовности:** после перезапуска сервера приложение восстанавливает доступ без ручной вставки временного access token.

### Этап 4/12. Довести OAuth до production-поведения

**Разработка:** реализовать обновление access token через refresh token, шифрование токенов, отзыв установки и маскирование секретов в логах. Добавить блокировку параллельного обновления токена.

**Что делает пользователь руками:** создаёт случайный `TOKEN_ENCRYPTION_KEY`, добавляет его в секреты хостинга и не помещает в Git. Один раз переустанавливает приложение для чистой проверки OAuth-цикла.

**Проверка:** тест искусственно просроченного access token автоматически получает новый токен.

**Критерий готовности:** приложение продолжает работать после истечения короткоживущего токена.

### Этап 5/12. Реализовать схему и валидатор рецепта

**Разработка:** создать allowlist шаблонов, измерений, показателей, фильтров и периодов. Проверить имена датасетов, имена полей, типы, длину строк и совместимость изменений.

**Что делает пользователь руками:** ничего. На этом этапе достаточно утвердить понятные тексты ошибок.

**Проверка:** unit-тесты принимают разрешённый рецепт и отклоняют неизвестные поля, произвольный SQL, код и опасные фильтры.

**Критерий готовности:** любой ответ модели проходит строгую проверку до чтения CRM и вызова REST API.

### Этап 6/12. Реализовать расчёт первого датасета

**Разработка:** получить сделки и менеджеров, применить период, исключить воронку «Тест», определить новых клиентов и сгруппировать результат по неделям. Добавить пагинацию, кэш и ограничение времени выполнения.

**Что делает пользователь руками:** готовит небольшой набор тестовых сделок с известным результатом или разрешает seed-скрипту создать его. После запуска сравнивает одну неделю с ручным расчётом.

**Проверка:** unit-тесты формулы и интеграционный тест на тестовом портале.

**Критерий готовности:** adapter стабильно возвращает строки в объявленной схеме.

### Этап 7/12. Подключить BitrixGPT как планировщик

**Разработка:** добавить tool schema для рецепта, системную инструкцию и ограничение числа попыток. Модель получает только доступные шаблоны и метаданные полей. При неподдерживаемом запросе она формирует заявку на развитие шаблонов.

**Что делает пользователь руками:** проверяет три формулировки одного запроса обычным языком и оценивает, понятно ли приложение пересказывает будущий расчёт.

**Проверка:** фразы дают одинаковый валидный рецепт, а запрос на неизвестный показатель не запускает публикацию.

**Критерий готовности:** BitrixGPT готовит структурированный черновик или понятную заявку на доработку.

### Этап 8/12. Сделать preview и diff

**Разработка:** показать название, колонки, формулу, период, фильтры и 3–10 примерных строк. Для обновления существующего датасета показать добавленные, скрытые и удаляемые поля.

**Что делает пользователь руками:** читает preview и нажимает «Опубликовать» только после проверки. Удаление поля или датасета требует отдельного явного подтверждения.

**Проверка:** до подтверждения в Битрикс24 не создаются и не изменяются объекты.

**Критерий готовности:** пользователь понимает результат до применения и может отменить операцию.

### Этап 9/12. Реализовать публикацию и обновление датасета

**Разработка:** создать коннектор и источник один раз, затем создавать датасеты по рецептам. Сохранять REST-id, версию рецепта и дату публикации. Безопасные изменения полей применять через `biconnector.dataset.fields.update`.

Переименование или смена типа используемого поля может сломать готовый график. Для таких изменений приложение предлагает создать версию датасета `v2`, а удаление полей выполняет только после предупреждения.

**Что делает пользователь руками:** подтверждает первую публикацию и отдельно подтверждает потенциально несовместимые изменения.

**Проверка:** опубликованный датасет появляется в «Рабочем месте аналитика», обновление схемы видно после синхронизации, удаление убирает только выбранный объект.

**Критерий готовности:** create, update, list и delete проходят end-to-end.

### Этап 10/12. Добавить интерфейс управления

**Разработка:** создать список опубликованных наборов со статусами «Черновик», «Опубликован», «Ошибка» и «Требует обновления». Добавить действия «Проверить данные», «Изменить описание», «Обновить схему» и «Удалить».

Надпись «Последняя синхронизация» показывает время последнего запроса BI-конструктора к adapter. Кнопка «Проверить данные» обновляет preview в нашем приложении. Принудительное очищение внутреннего кэша нативного BI обещаем только после подтверждения отдельного API.

**Что делает пользователь руками:** проверяет понятность статусов и выполняет полный сценарий без терминала.

**Проверка:** интерфейс корректно переживает перезагрузку и показывает сохранённые REST-id и ошибки.

**Критерий готовности:** для обычной публикации терминал больше не нужен.

### Этап 11/12. Собрать нативный график вручную

**Разработка:** подготовить точную инструкцию и проверить, что датасет доступен в BI-конструкторе.

**Что делает пользователь руками как аналитик:** выполняет процедуру из раздела 9 этого документа. Это обязательная ручная часть проекта. Приложение готовит данные, а пользователь выбирает способ их показа.

**Проверка:** нативный график показывает конверсию по неделям и менеджерам, после изменения данных CRM значения обновляются без пересоздания графика.

**Критерий готовности:** опубликованный набор используется в сохранённом нативном отчёте.

### Этап 12/12. Проверить, описать и выпустить

**Разработка:** провести E2E-тест, нагрузочную проверку, аудит логов и зависимостей. Обновить README, setup, ограничения и сценарий второй статьи.

**Что делает пользователь руками:** повторяет инструкцию с чистого клона, делает скриншоты фразы, preview, опубликованного датасета и готового нативного графика. Затем сверяет итоговые числа с тестовым набором.

**Проверка:** `npm run lint`, `npm test`, покрытие не ниже 70% с целью 80%, `npm audit --audit-level=high` и отдельный E2E-чек-лист.

**Критерий готовности:** другой пользователь может клонировать проект, подключить свой портал и воспроизвести сценарий по README.

## 9. Что аналитик делает руками

После публикации каждого нового датасета аналитик выполняет один раз следующие действия:

1. Открывает «BI-конструктор» → «Рабочее место аналитика» и проверяет, что новый датасет появился в списке таблиц.
2. Создаёт отчёт или открывает нужный нативный дашборд и нажимает «Создать график».
3. Выбирает опубликованный датасет и тип графика, например линейный.
4. Перетаскивает `WEEK_START` в ось времени, `CONVERSION_RATE` в показатель, а `MANAGER_NAME` в группировку или серии.
5. Настраивает подписи, цвета и визуальные фильтры, сохраняет график и размещает его на дашборде.

Эта работа сохраняется в BI-конструкторе. При следующих запросах данных adapter пересчитывает строки, поэтому аналитик не собирает тот же график заново. Ручная доработка понадобится, когда пользователь создаст новый датасет с другой структурой или подтвердит несовместимое изменение полей.

## 10. Что пользователю придётся настроить вне кода

### Один раз при установке

1. Получить постоянный публичный HTTPS-адрес для adapter-сервиса.
2. Создать и установить локальное приложение Битрикс24 с нужными правами.
3. Добавить секреты OAuth и шифрования в переменные окружения хостинга.

### Для демонстрации статьи

1. Подготовить тестовые сделки и воронку «Тест» или запустить безопасный seed-скрипт.
2. Подтвердить рецепт и публикацию в интерфейсе приложения.
3. Один раз собрать график в нативном BI-конструкторе по инструкции выше.

### При обычной работе

Пользователь формулирует запрос, проверяет preview и подтверждает публикацию. Аналитик создаёт нативный график для каждого принципиально нового набора данных. Техническое обновление строк, OAuth-токенов и статусов выполняет сервер.

## 11. Правила безопасности

- BitrixGPT не получает токены, содержимое карточек клиентов и сырые персональные данные.
- Модель не генерирует SQL, JavaScript или URL источников. Она выбирает только значения из серверного каталога возможностей.
- Публикация и несовместимые изменения требуют preview и явного подтверждения пользователя.
- Adapter принимает запросы только от настроенного источника, ограничивает размер ответа и не пишет данные строк в логи.
- OAuth-токены шифруются, refresh token обновляется атомарно, секреты хранятся вне Git.

## 12. Тестовая стратегия

### Unit-тесты

Покрыть валидатор рецепта, правила именования, формулы конверсии, diff схемы и обновление OAuth-токена. Добавить отрицательные случаи для произвольного кода, неизвестных полей и неверных типов.

### Интеграционные тесты

Проверить REST-клиент на записанных обезличенных ответах Битрикс24, adapter-протокол и постоянное хранилище. Сетевые ошибки, тайм-ауты и повторные запросы должны давать предсказуемый результат.

### End-to-end

На тестовом портале выполнить три сценария: первая публикация, совместимое добавление поля и создание `v2` при несовместимом изменении. После каждого сценария проверить нативный график и журнал без персональных данных.

Минимальное покрытие — 70%, целевое — 80%. Линтер, тесты и аудит зависимостей запускаются при каждом изменении кода.

## 13. Основные риски

| Риск | Как снижаем |
|---|---|
| Публичный callback закрыт Gateway или нестабилен. | Используем отдельный постоянный HTTPS-адрес и проверяем его с внешней сети до создания коннектора. |
| OAuth-токен истёк или отозван. | Автоматически обновляем токен, показываем статус установки и даём понятный сценарий переустановки. |
| Изменение схемы ломает готовый график. | Показываем diff, сохраняем версии и создаём `v2` для несовместимых изменений. |
| BitrixGPT неверно понял бизнес-термин. | Используем шаблоны, preview и подтверждённые определения показателей. |
| Расчёт не успевает ответить BI-конструктору. | Ограничиваем период, используем пагинацию, кэш и заранее рассчитанные агрегаты для больших объёмов. |
| В логи попадают данные CRM. | Логируем идентификатор запроса, время и число строк без содержимого строк и токенов. |

## 14. Критерии готовности первой версии

1. Фраза о конверсии превращается в валидный рецепт, preview и понятный diff.
2. После подтверждения датасет появляется в «Рабочем месте аналитика» без терминала.
3. Adapter возвращает актуальные строки по схеме и фиксирует время последней синхронизации.
4. Аналитик создаёт нативный график, который продолжает работать после обновления данных CRM.
5. Совместимое изменение полей применяется после preview, несовместимое создаёт новую версию датасета.
6. Удаление требует подтверждения и удаляет только выбранный датасет.
7. Секреты и содержимое карточек не появляются в браузере, контексте BitrixGPT и логах.
8. README позволяет повторить установку с чистого клона.

## 15. Решения, которые нужно подтвердить до начала кода

1. Как в тестовом портале определяется новый клиент: по полю CRM, первой сделке или отдельному признаку.
2. Какая стадия или семантика считается успешной сделкой.
3. Где будет размещён постоянный публичный adapter и какой URL получит локальное приложение.

Первые два решения подтверждает владелец бизнес-сценария. Третье решение принимается при начале этапа 2/12.
