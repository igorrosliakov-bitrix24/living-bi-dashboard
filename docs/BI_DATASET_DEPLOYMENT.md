# Постоянная публикация датасета в нативный BI-конструктор

Этот документ описывает переход от уже подтверждённой проверки к постоянно работающему источнику данных для нативного BI-конструктора Битрикс24.

## Что уже подтверждено

Проверочный сценарий прошёл полный путь:

1. Локальное OAuth-приложение со scope `biconnector` получило доступ к REST API Битрикс24.
2. Скрипт создал BI-коннектор, источник и датасет.
3. Датасет появился в «Рабочем месте аналитика».
4. Нативный отчёт «Проверка REST-датасета VibeCode» получил из adapter три строки и показал их в таблице.

Это доказывает полезную границу API: приложение способно передать подготовленную таблицу данных в нативный BI-конструктор. Настройки уже созданных нативных графиков этим API не меняются.

В редакторе нативного графика тестовый датасет отдал три строки.

## Что развёрнуто

- `adapter-server.js` реализует HTTP-контракт BI-коннектора: проверка, список таблиц, схема и строки.
- `deploy/living-bi-adapter.service` запускает adapter через systemd на порту `3000` и автоматически перезапускает его после сбоя.
- `deploy/adapter.env.example` показывает переменные, которые хранятся только на сервере.
- Adapter не записывает в журнал значения строк, OAuth-токены или ключи; журнал содержит маршрут, технические имена полей и код таблицы. Дополнительно он сохраняет безопасный статус: время последнего запроса и последнего успешного ответа, код таблицы и счётчик запросов.

## Что требуется для постоянной работы

### 1. Открытый callback-адрес

Битрикс24 BI-коннектор вызывает `urlCheck`, `urlTableList`, `urlTableDescription` и `urlData` сам. Поэтому эти URL должны быть доступны порталу по стабильному HTTPS-адресу без Gateway-сессии.

Подходят два варианта:

1. Отдельное VibeCode-приложение для adapter-а: его HTTPS-поддомен `https://app-...vibecode.bitrix24.tech` остаётся в режиме Black Hole, но политика доступа меняется на `PUBLIC`. Это открывает именно HTTPS-приложение для серверных запросов Битрикс24. Режим `OPEN` для этого не нужен: он открывает прямой IP и SSH, а не решает задачу callback.
2. Для adapter используется постоянный собственный домен с HTTPS, например через Cloudflare Tunnel с закреплённым hostname.

Временный Quick Tunnel полезен для отладки, однако его адрес меняется после перезапуска и для production не используется.

Проверка 20.08.2026 уточнила ситуацию: существующее VibeCode-приложение `living-bi-dashboard` имеет постоянный HTTPS-адрес, но находится в `accessPolicy: OWNER_ONLY` и засыпает. Его нельзя открывать публично, потому что там находится пользовательский интерфейс. Для production нужно развернуть отдельное adapter-приложение, выставить только ему `accessPolicy: PUBLIC` и исключить сон; затем его HTTPS-адрес можно использовать в BI-коннекторе.

### 2. OAuth локального приложения

Создайте локальное приложение Битрикс24 со scope `biconnector`. В его настройках укажите:

| Поле Битрикс24 | Значение |
|---|---|
| Путь обработчика | `https://<постоянный-домен>/bitrix/handler` |
| Путь первоначальной установки | `https://<постоянный-домен>/bitrix/install?install_secret=<случайная-строка>` |
| Использует только API | включено |
| Права | `Коннектор BI-аналитики (biconnector)` |

На сервере создайте файл `/etc/living-bi-adapter.env` на основе `deploy/adapter.env.example`. Добавьте уникальный `BITRIX24_INSTALL_SECRET`; `BITRIX24_APPLICATION_TOKEN` остаётся дополнительной второй проверкой, но для установки достаточно `install_secret`. Доступ к файлу должен быть только у системного пользователя сервиса.

После установки Битрикс24 отправляет `access_token` и `refresh_token` в `/bitrix/install`. Adapter проверит секрет и сохранит их в `OAUTH_ADAPTER_STATE_PATH`. Он автоматически обновляет `access_token` через `refresh_token` до истечения срока действия. Если задан `OAUTH_STATE_ENCRYPTION_KEY`, файл на диске шифруется AES-256-GCM; для постоянного развёртывания это обязательная настройка.

### 3. Создание коннектора, источника и датасета

Когда постоянный callback и OAuth уже настроены, в рабочем окружении задают:

```dotenv
BITRIX24_PORTAL_URL=https://your-portal.bitrix24.ru
BITRIX24_OAUTH_ACCESS_TOKEN=<temporary-access-token>
BI_CONNECTOR_BASE_URL=https://bi-data.example.com
```

Для короткой проверки запустите:

```bash
npm run bi:connector-demo -- --confirm --hold-seconds=300
```

Скрипт создаёт временные объекты и удаляет их после заданной паузы. Для постоянного источника нужен отдельный сценарий идемпотентной синхронизации: он находит существующие объекты по сохранённым ID, обновляет схему и данные, затем показывает статус последней успешной передачи.

## Что добавлено в пользовательский интерфейс

- Безопасный BitrixGPT Planner с allowlist единственного шаблона.
- Preview и подтверждение черновика без вызова Dataset API.
- Read-only readiness-проверка публичного callback URL, OAuth-state и OAuth-пары.
- Отдельная кнопка «Опубликовать в BI-конструктор» с typed-confirmation `publish_dataset`.
- Идемпотентная публикация: если `vibecode_ai_deal_intake_weekly` уже существует, новые BI-объекты не создаются.
- Статус синхронизации: интерфейс показывает время последнего обращения BI-конструктора к adapter-у и число запросов, не раскрывая строки данных.
- Управляемое удаление: отдельная раскрывающаяся секция требует точную фразу `delete_dataset`, удаляет только датасет с префиксом `vibecode_ai_` и не затрагивает коннектор, источник, CRM или отчёты.

Живое нажатие кнопки публикации должно выполняться только после явного согласия владельца портала. Readiness должна подтверждать не просто HTTP `200`, а JSON-ответ adapter-а без Gateway: Galaxy Black Hole может вернуть HTML-страницу с тем же статусом и не подходит для callback BI-коннектора.

## Временное восстановление 20.08.2026

На интеграционном портале уже существовали коннектор ID 1, источник ID 1 и датасет `vibecode_ai_deal_intake_weekly` ID 7. Повторную публикацию не выполняли. Вместо этого локальный adapter запустили на порту 3001 с существующим OAuth-state, подняли Cloudflare Quick Tunnel и обновили только четыре callback URL коннектора. Публичные `/health` и `/bi-connector/data` вернули JSON, а схема датасета совпала с восемью ожидаемыми полями.

Ручная проверка в нативном BI-конструкторе подтвердила цепочку целиком: таблица открылась, определила источник VibeCode AI и показала реальные агрегированные строки по неделям, менеджерам и валютам. Схему не изменяли и повторно не сохраняли.

Это временный контур. Остановка локального adapter или Quick Tunnel сделает источник недоступным, а новый URL потребует обновить callback URL коннектора. Для постоянной работы нужен HTTPS-адрес без Gateway.

## Что остаётся для production-готовности

1. Создать отдельное VibeCode-приложение только для adapter-а, развернуть в нём adapter и установить `accessPolicy: PUBLIC`. Это требует явного подтверждения, потому что адрес станет доступен из интернета.
2. Отключить засыпание для этого отдельного приложения либо подтвердить, что его автоматическое пробуждение возвращает BI-коннектору рабочий ответ без ошибки `BH_SERVER_WAKING`.
3. В защищённом окружении приложения задать `OAUTH_STATE_ENCRYPTION_KEY` и перенести OAuth-state на постоянный том `/data`.
4. Обновить четыре callback URL существующего коннектора на HTTPS-адрес отдельного adapter-а и вручную проверить таблицу в BI-конструкторе.

Эта ветка расширяет продукт, но не заменяет AI-редактор. AI-редактор меняет безопасную JSON-конфигурацию собственного дашборда. Публикация датасета передаёт подготовленную таблицу в нативный BI-конструктор, где аналитик собирает графики штатными средствами Битрикс24.

## Фактическое завершение постоянного контура (23.08.2026)

Пункты production-готовности для первого набора данных выполнены.

- Выделенный VibeCode-сервер `living-bi-dataset-adapter` работает в режиме `PUBLIC`, использует постоянный HTTPS-поддомен и не засыпает.
- Adapter запущен отдельным сервисом на порту 3000. OAuth-state хранится на постоянном диске в зашифрованном виде, а access token обновляется по refresh token.
- Локальное OAuth-приложение переустановлено на постоянные адреса adapter-а.
- Четыре URL существующего коннектора ID `1` переключены через `biconnector.connector.update`; повторная публикация источника и датасета не выполнялась.
- Внешне подтверждены ответы всех четырёх callback-маршрутов. Проверка данных ограничивалась одной агрегированной строкой.

Пользовательская проверка в нативном BI выполнена: портал открыл `vibecode_ai_deal_intake_weekly`, показал восемь колонок и реальные агрегированные строки. Это подтвердило обращение самого портала к постоянному adapter-у.
