# Техническая разведка Вайбкода

**Дата:** 07.08.2026  
**Статус:** в работе  
**Среда:** тестовый портал `b24-w9apyi.bitrix24.ru`, тариф NFR

Документ хранит только безопасные результаты проверок. Ключи, OAuth-токены и персональные данные здесь не фиксируются.

## Подтверждено

### Репозиторий и окружение

- Локальная ветка `main` синхронизирована с `origin/main`.
- Удалённый репозиторий: `https://github.com/igorrosliakov-bitrix24/living-bi-dashboard.git`.
- В `.env` присутствуют личный ключ `VIBECODE_API_KEY` и ключ приложения `VIBECODE_APP_KEY`.
- `.env` исключён из Git.

### Ключ приложения

`GET /v1/me` с ключом `vibe_app_...` вернул `200`.

Ключ привязан к нужному порталу и содержит скоупы:

- Битрикс24: `crm`, `task`, `tasks`, `user`, `placement`;
- Вайбкод: `vibe:infra`, `vibe:ai`, `vibe:storage`, `vibe:search`.

Набор покрывает требования PRD для MVP.

### OAuth-сессия

Запросы к `deals`, `tasks` и `companies` с одним ключом приложения возвращают `401 TOKEN_MISSING`. Это ожидаемое поведение.

Для доступа к данным пользователя BFF должен:

1. отправить пользователя на `GET /v1/oauth/authorize`;
2. получить одноразовый код на callback;
3. обменять код через `POST /v1/oauth/token`;
4. хранить полученный `vibe_session_...` только на сервере;
5. передавать ключ приложения в `X-Api-Key`, а сессию пользователя в `Authorization: Bearer`.

### Сущности

`GET /v1/guide` доступен по ключу приложения без пользовательской сессии и возвращает 23 сущности.

Для MVP подтверждены:

- `deals`;
- `companies`;
- `tasks`;
- `activities`;
- `deal-categories`;
- `task-comments`.

Отдельной сущности `/v1/calls` нет: запрос возвращает `404 ROUTE_NOT_FOUND`. Звонки нужно искать среди `activities` и проверять их типы и поля после получения OAuth-сессии.

### Места встраивания

`GET /v1/placements/available` с ключом приложения вернул `200`.

`BI_ANALYTICS_MENU` в текущем динамическом справочнике отсутствует. Для MVP следует планировать обычную встройку приложения в меню или на страницу Битрикс24. Повторную проверку можно выполнить перед финальным деплоем.

## Принятые решения

1. Личный `vibe_api_...` используется для локальной диагностики, seed-скрипта и фоновых задач разработчика.
2. Ключ `vibe_app_...` используется BFF для OAuth и работы приложения от имени пользователя.
3. Ключи остаются на сервере и не передаются во frontend.
4. Основной вариант встройки MVP — обычный пункт меню/страница приложения.
5. Источником звонков предварительно считаются `activities`; это нужно подтвердить реальными метаданными.

## Остаётся проверить

- полный OAuth-поток и время жизни пользовательской сессии;
- `fields`, `statuses` и `aggregate` после OAuth;
- типы звонков в `activities`;
- function calling модели `bitrixgpt-5.5`;
- постоянное хранилище и деплой на Black Hole;
- фактические лимиты из заголовков ответов;
- конкретный placement для обычной встройки.

## Следующий этап

Реализовать минимальный OAuth-контур:

- `GET /auth/login`;
- `GET /auth/callback`;
- серверное хранение `state` и пользовательской сессии;
- `GET /api/session` без возврата OAuth-токенов;
- тесты успешного входа, неверного `state`, истёкшего кода и отсутствующей сессии.

После OAuth проверить реальные поля и агрегаты сделок, компаний, задач и активностей.
