## Подтверждено

### Репозиторий и окружение

- Локальная ветка `main` синхронизирована с `origin/main`.
- Удалённый репозиторий: `https://github.com/igorrosliakov-bitrix24/living-bi-dashboard.git`.
- В `.env` присутствуют личный ключ `VIBECODE_API_KEY` и ключ приложения `VIBE_APP_KEY` (для обратной совместимости локально читается также `VIBECODE_APP_KEY`).
- `.env` исключён из Git.

### Ключ приложения

`GET /v1/me` с ключом `vibe_app_...` вернул `200`.

Ключ привязан к нужному порталу и содержит скоупы:

- Битрикс24: `crm`, `task`, `tasks`, `user`, `placement`;
- Вайбкод: `vibe:infra`, `vibe:ai`, `vibe:storage`, `vibe:search`.

Набор покрывает требования PRD для MVP.

### Gateway-сессия для Black Hole

Запросы к `deals`, `tasks` и `companies` с одним ключом приложения возвращают `401 TOKEN_MISSING`. Это ожидаемое поведение.

Для приложения, развёрнутого в Black Hole, отдельный OAuth-экран не нужен. Поток выглядит так:

1. размещение в Битрикс24 открывает `https://vibecode.bitrix24.tech/v1/bitrix-handler`;
2. Gateway определяет пользователя и отправляет запрос на сервер с `X-Vibe-Authorization: Bearer vibe_session_...`;
3. сервер передаёт этот заголовок в V1 API как `Authorization`, добавляя `VIBE_APP_KEY` в `X-Api-Key`;
4. браузер токен сессии не видит и не хранит;
5. при `401` пользователь заново открывает приложение из меню Битрикс24.

### Сущности

`GET /v1/guide` доступен по ключу приложения без пользовательской сессии и возвращает 23 сущности.

Для MVP подтверждены:

- `deals`;
- `companies`;
- `tasks`;
- `activities`;
- `deal-categories`;
- `task-comments`.

Отдельной сущности `/v1/calls` нет: запрос возвращает `404 ROUTE_NOT_FOUND`. Звонки нужно искать среди `activities` и проверять их типы и поля в Gateway-сессии.

### Агрегаты дашборда

- Подтверждён `POST /v1/deals/aggregate`: для виджета с `count` и группировкой `stageId` API вернул 10 сделок.
- В тестовой выборке по стадиям: `WON` — 5, `LOSE` — 1, `NEW` — 2, `PREPARATION` — 2. Признак `truncated` равен `false`.
- BFF отдаёт фронтенду только итоговые числа и группы, без карточек сделок и персональных данных.
- Endpoint `GET /api/dashboard/data` строит агрегатные запросы из валидированной JSON-спеки. В production он использует Gateway-сессию, локально — личный ключ разработчика.
- Endpoint `POST /api/dashboard` создаёт новую версию спеки только после проверки JSON, ожидаемой версии и допустимых полей. В production редактирование доступно Gateway-сессии администратора.
- История версий сохраняется атомарно в JSON-файл: локально — в исключённую из Git папку `.data`, в Galaxy — в `/data/living-bi-dashboard/dashboard-state.json`. Диагностическая команда в Galaxy подтвердила, что `/data` смонтирован отдельным ext4-том, а каталог приложения использует временный overlay-слой. Восстановление выбирает существующую версию текущей и не создаёт новый снимок.
- AI Router проверен на модели `bitrix/bitrixgpt-5.5`: `POST /v1/chat/completions` с `response_format: json_object` вернул корректный JSON. Для ИИ-редактора используется только этот канонический маршрут, без устаревшего `/v1/ai/chat/completions`.

### Места встраивания

`GET /v1/placements/available` с ключом приложения вернул `200`.

`BI_ANALYTICS_MENU` в текущем динамическом справочнике отсутствует. Для MVP следует планировать обычную встройку приложения в меню или на страницу Битрикс24. Повторную проверку можно выполнить перед финальным деплоем.

### Деплой и placement

- Для проекта создано отдельное Galaxy-приложение `living-bi-dashboard` с адресом `https://app-daffcac4becb.vibecode.bitrix24.tech`.
- Платформа выбрала тип `GALAXY_APP`: код загружается встроенным архивом, а не по внешней ссылке. Архив исключает `.env`, `.git`, `node_modules`, `coverage` и рабочие каталоги.
- Деплой выполнен на Node 20. В окружение сервера переданы только `NODE_ENV=production` и `VIBE_APP_KEY`; личный ключ `vibe_api_...` в приложение не передаётся.
- Статус после деплоя: `running`, `blackholeStatus: CONNECTED`. В логах подтверждён запуск Node-процесса на `0.0.0.0:3000`.
- Приложение привязано к `LEFT_MENU` с подписью «AI-редактор BI-отчётов». Платформа заменила технический URL на `https://vibecode.bitrix24.tech/v1/bitrix-handler`, что необходимо для Gateway-сессии.
- Финальная интерактивная проверка требует войти в тестовый портал и открыть пункт левого меню: браузер разработки не авторизован на портале.

### API датасетов BI-конструктора

OAuth-приложение со scope `biconnector` создало коннектор, источник и датасет через REST API Битрикс24. Нативный BI-конструктор получил от adapter три демонстрационные строки и разместил таблицу на дашборде. Детали проверки и скриншоты находятся в [BI_DATASET_EXPERIMENT.md](BI_DATASET_EXPERIMENT.md).

## Принятые решения

1. Личный `vibe_api_...` используется для локальной диагностики, seed-скрипта и фоновых задач разработчика.
2. Ключ `vibe_app_...` используется BFF для Gateway-сессии и работы приложения от имени пользователя.
3. Ключи остаются на сервере и не передаются во frontend.
4. Основной вариант встройки MVP — обычный пункт меню/страница приложения.
5. Источником звонков предварительно считаются `activities`; это нужно подтвердить реальными метаданными.
6. Встройка MVP использует `LEFT_MENU`; размещение зарегистрировано через `bitrix-handler`.
