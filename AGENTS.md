## Что мы разрабатываем

В репозитории есть два связанных контура.

### 1. AI-редактор собственного дашборда

Это отдельное приложение внутри Битрикс24, размещённое рядом с нативным BI-конструктором. Оно получает агрегаты портала, хранит собственную JSON-конфигурацию дашборда и позволяет менять поддерживаемые настройки через BitrixGPT.

Основной сценарий:

```text
placement Битрикс24
  -> Gateway Вайбкода
  -> server.js (BFF)
  -> VibeCode API: поля, агрегаты и BitrixGPT
  -> собственный дашборд и версии конфигурации
```

Приложение не читает и не меняет конфигурацию готовых нативных BI-отчётов. Поддерживаемые изменения применяются только к JSON-схеме нашего дашборда. Когда возможностей схемы недостаточно, BitrixGPT формирует структурированную заявку для агента разработки.

### 2. AI Dataset Publisher для нативного BI

Это следующий этап проекта. Пользователь описывает нужный набор данных словами, BitrixGPT готовит безопасный рецепт, сервер проверяет его и публикует датасет через REST API `biconnector`. После этого аналитик один раз вручную создаёт на датасете график в нативном BI-конструкторе.

Основной сценарий:

```text
пользовательская фраза
  -> BitrixGPT Planner
  -> валидируемый рецепт датасета
  -> preview и подтверждение
  -> OAuth REST API biconnector
  -> публичный adapter-server.js
  -> Рабочее место аналитика
  -> ручная сборка нативного графика
```

API датасетов управляет источниками и составом полей. Изученные методы не дают доступа к типу графика, фильтрам и раскладке готового нативного отчёта.

## Контур `b24-w9apyi` (23.08.2026)

Три сервера VibeCode, у каждого своя роль. Путать их нельзя.

| Сервер | Роль | Тариф | Политика | Адрес |
|---|---|---|---|---|
| `living-bi-dashboard-vm` | интерфейс AI-редактора, placement `LEFT_MENU` | bc-agent | `OWNER_ONLY` | `app-fb0a764f1d08` |

Интерфейс обязан оставаться `OWNER_ONLY`: он открывается через Gateway изнутри портала. Adapter обязан быть `PUBLIC`: Битрикс24 вызывает его четыре callback URL сервер-к-серверу без сессии Вайбкода. Из-за разных политик доступа интерфейс и adapter не могут жить на одном сервере.

### Как выкладывать adapter

SSH использовать не нужно: серверы в режиме `BLACKHOLE` не имеют внешнего маршрута. Все операции идут через Deploy API поверх туннеля, и он сам ставит systemd-юнит.

```text
POST /v1/infra/servers/:id/deploy
  runtime=node20, start="node adapter-server.js", healthPath="/health",
  serviceName="app", dataDirs=["/opt/data/state"]
```

Правила, которые уже стоили времени:

- Перед каждым deploy прочитать карточку сервера и проверить `kind`. Для `GALAXY_APP` архив считать полной заменой кода приложения: обязательно включать `package.json`, точку запуска, все локальные модули и `public/`. Частичный архив через `/deploy` запрещён; для точечного обновления использовать `/upload` только после проверки контракта.
- Перед отправкой проверить безопасный список содержимого архива. Если после deploy журнал сообщает об отсутствующем `package.json` или модуле, это дефект архива, а не инфраструктурный `EXEC_BUSY`; сначала восстановить тот же сервер полным архивом.

- `/opt/app` очищается при каждом деплое. Постоянное состояние — только в `dataDirs`, у нас это `/opt/data/state`.
- У нового сервера авто-сон включён на 60 минут. Снимать явно: `PATCH /sleep` с `{"sleepAfterMinutes": null}`; других значений, кроме `15 | 30 | 60 | 240 | null`, эндпоинт не принимает.
- Тариф через API не меняется. `PATCH /v1/infra/servers/:id` — переименование; смена плана делается пересозданием сервера. Самый дешёвый план — `bc-agent`, 300 ₩/мес.
- `accessPolicy` менять только по явному подтверждению пользователя: `PATCH /v1/infra/servers/:id/access-policy`.
- Диагностика: `GET /v1/infra/servers/:id` (`runtimeStatus`, `buildLog`), `GET /logs?service=app`, `POST /exec`. Если `service: null` и в журнале только записи ОС — деплой не доходил до сервера ни разу.

### Размещение: выделенная VM, не galaxy

Платформа по умолчанию кладёт новое приложение на общий galaxy-хост (`resolvedDeployMode: "galaxies-only"`). Выделенная машина создаётся **только** при явном `placement: "dedicated"` в `POST /v1/infra/servers`. Все три сервера проекта должны быть выделенными.

У galaxy-приложения нет своей VM: при падении общего хоста не работают ни `/wake`, ни `/reboot`, ни `/exec`, ни чтение логов — восстановить его нельзя ничем, кроме ожидания. Плюс оно засыпает и делит хост с чужими приложениями. Для интерфейса, встроенного в портал, это неприемлемо.

### Архив без npm

Сборка выполняет `npm ci` только при `[ ! -d node_modules ]`. У приложения ноль runtime-зависимостей, поэтому в архив кладётся пустой каталог `node_modules/` — шаг установки не запускается, и выкладка не зависит от сети сборочного контейнера. Без этого деплой падает с `npm error code ETIMEDOUT`.
